# CoCompose 배포 방식 결정

작성일: 2026-09-10
대상: `docs/review-next-milestones-2026-09-10.ko.md`의 N5

N5는 배포 방식·코드 서명·업데이트 채널을 "명시적으로 결정"하라고 요구한다. 아래가 그 결정과 이유다. 기본값을 그냥 따라간 것이 아니라 각각을 고르고 그 대가를 적었다.

## 결정 요약

| 항목 | 결정 | 이유 |
|---|---|---|
| 배포 형식 | 이식형 ZIP 하나 | 압축만 풀면 실행된다. 관리자 권한도 설치 과정도 필요 없다 |

| 제거 | 설치 폴더의 `Uninstall.cmd` | 프로그램과 바로가기만 지우고 프로젝트는 남긴다 |

## 배포 형식: 이식형 ZIP

`CoCompose-<버전>-windows-x64.zip` 하나가 배포물이다. 안에는 실행 파일, 이 빌드가 무엇인지 적은 `BUILD-INFO.json`, 변경 기록, 라이선스, 외부 도구용 `tools/cocompose.py`, 그리고 이 빌드에 실제로 돌린 검사 결과가 든 `verification/`이 들어 있다.

압축을 풀고 `CoCompose.exe`를 두 번 누르면 실행된다. Visual Studio도 CMake도 Python도 필요 없다. 이것은 CI가 매번 확인한다(`tools/test_portable_start.ps1`이 개발 도구가 하나도 닿지 않는 PATH로 실행한다).

## 설치와 제거

설치를 원하면 ZIP 안의 `Install.cmd`를 실행한다. 하는 일은 세 가지다.

1. 폴더를 `%LOCALAPPDATA%\Programs\CoCompose`로 복사한다. 사용자 자기 영역이므로 관리자 권한이 필요 없다.
2. 시작 메뉴에 바로가기를 만든다.
3. 같은 폴더에 `Uninstall.cmd`를 남긴다.

프로젝트는 `Documents\CoCompose`에 있고 설치 폴더 밖이다. 그래서 같은 `Install.cmd`를 새 빌드로 다시 실행하는 것이 곧 업데이트이며, 작업물은 그대로 남는다. `Uninstall.cmd`는 프로그램과 바로가기만 지우고 프로젝트에는 손대지 않는다.

`tools/test_install_and_update.ps1`이 이 흐름 전체를 확인한다. 설치 → 프로젝트 작성 → 같은 설치 반복(업데이트) → 프로젝트가 그대로인지 → 제거 → 프로젝트가 여전히 남아 있는지. 개발 도구가 없는 PATH에서 돌린다.

### 설치 EXE를 만들지 않는 이유

NSIS 같은 것으로 설치 EXE를 만들 수는 있다. 하지만 이 프로그램이 설치 시점에 하는 일은 폴더 복사와 바로가기 생성뿐이라 EXE가 더 해주는 것이 없다. 반대로 서명되지 않은 설치 EXE는 SmartScreen이 더 강하게 막고, 빌드 파이프라인에 검증할 것이 하나 더 늘어난다. 배치 파일은 사용자가 열어서 무엇을 하는지 읽을 수 있다는 점도 서명이 없는 상황에서는 장점이다.

레지스트리의 "프로그램 추가/제거" 목록에도 등록하지 않는다. 등록하려면 `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall`에 항목을 쓰면 되지만, 지금은 제거가 폴더 안의 스크립트 하나로 끝나므로 상태를 두 군데로 늘리지 않는다.

## 코드 서명: 하지 않는다

서명하려면 인증서를 사야 하고(OV는 연 수십만 원대, EV는 더 비싸고 하드웨어 토큰이 따라온다), 그 키를 CI에 넣어야 한다. 이 프로젝트는 개인용 포크이고 공개 배포처가 없다. 비용과 키 관리 부담이 얻는 것보다 크다.

대신 다음을 한다.

- 배포물 옆에 `SHA256SUMS.txt`를 함께 낸다. 해시는 검사가 끝나고 검사 보고서까지 ZIP에 들어간 뒤에 계산하므로, 내려받은 파일 그대로의 해시다.
- ZIP 안의 `BUILD-INFO.json`이 버전, 만들어진 커밋, 빌드 시각, 실행 파일의 SHA-256, 그리고 그 커밋의 작업 트리가 깨끗했는지를 적는다.

확인 방법은 다음과 같다.

```
Get-FileHash CoCompose-0.1.0-windows-x64.zip -Algorithm SHA256
```

이 값을 `SHA256SUMS.txt`와 비교한다. 실행 파일만 따로 확인하려면 압축을 푼 뒤 `BUILD-INFO.json`의 `sha256`과 비교한다.

**대가**: 처음 실행할 때 Windows SmartScreen이 "알 수 없는 게시자"라며 막는다. `추가 정보` → `실행`을 눌러야 한다. 서명하지 않기로 한 이상 이것은 숨길 수 없는 결과이고, 문서에 적어두는 편이 낫다. 서명이 필요해지는 시점은 이 빌드를 남에게 배포하기 시작할 때다.

## 업데이트 채널: 수동

자동 업데이트를 넣지 않는다. 앱이 네트워크에 나가지 않으며(`JUCE_USE_CURL=0`, `NEEDS_CURL FALSE`), 서명이 없는 상태에서 자동 업데이트는 서명 없는 바이너리를 스스로 내려받아 실행하는 경로를 만드는 일이다. 그건 지금 얻을 것보다 위험이 크다.

대신 이렇게 한다.

1. 새 빌드는 CI가 검사를 통과했을 때만 artifact로 올라간다.
2. 사용자는 그 ZIP을 내려받아 압축을 풀고, 이식형으로 쓰거나 `Install.cmd`를 다시 실행한다.
3. `BUILD-INFO.json`의 `version`과 `commit`으로 지금 쓰는 것이 어떤 빌드인지 확인한다.
4. 프로젝트는 설치 폴더 밖에 있으므로 업데이트가 작업물을 건드리지 않는다.

## 검사를 통과하지 못한 빌드는 나가지 않는다

**CI는 수동으로만 돈다.** push·pull request·schedule 트리거를 전부 뺐고 `workflow_dispatch`만 남겼다. 이 fork는 상위 저장소에서 물려받은 워크플로(`build`, `generate_coverage`, `juce_compat`, `update_docs`)를 함께 들고 있는데, 그것들이 push마다 12개 Debug 매트릭스를 돌린다. public 저장소에서는 무료지만 private 저장소에 같은 코드를 올리면 그대로 과금된다. 검사가 필요한 시점은 사람이 정한다.

돌리는 방법은 GitHub의 Actions 탭에서 워크플로를 고르고 `Run workflow`를 누르거나, `gh workflow run cocompose-windows.yml --ref ai-editor`다.

`.github/workflows/cocompose-windows.yml`이 순서를 강제한다. 빌드 → 패키징 → ZIP 압축 해제 → 압축을 푼 실행 파일로 통합 검사 26개 → 두 번 누른 것처럼 시작되는지 → 설치·업데이트·제거 → 봉인이 잘못된 보고서를 거절하는지 → 봉인 → 그다음에야 ZIP과 `SHA256SUMS.txt`를 올린다. 앞 단계가 하나라도 실패하면 workflow가 실패하고 배포물은 올라가지 않는다.

봉인은 검사 보고서를 그냥 첨부하지 않고 읽는다. 아는 형식인지, 통과라고 적혀 있는지, 검사 수가 최소치 이상인지, 그리고 그 보고서가 검사한 실행 파일이 이 ZIP 안의 실행 파일과 같은지를 확인한다. 마지막 항목이 없으면 아무 빌드의 보고서로 아무 배포물이나 봉인할 수 있다. 실패한 보고서, 다른 빌드의 보고서, JSON이 아닌 파일, 지정한 첨부 문서가 없는 경우는 모두 거절되며 `tools/test_release_seal.ps1`이 그것을 검사한다.

이 gate는 실제로 두 번 나쁜 빌드를 막았다. 한 번은 렌더용 Edit를 작업 스레드에서 만들어 러너에서 멈춘 빌드였고(로컬에서는 통과했다), 한 번은 오디오 장치가 없는 러너에서 녹음 검사가 걸린 경우였다.

검사 보고서는 두 곳에 있다. workflow의 `CoCompose-check-report` artifact, 그리고 배포 ZIP 안의 `verification/` 폴더다. 후자가 있는 이유는 파일 하나만 들고 있어도 그 빌드에 무엇이 돌았는지 알 수 있게 하기 위해서다.

## 남는 한계

- 서명이 없어 SmartScreen 경고가 뜬다.
- 자동 업데이트가 없다.
- x64 Windows만 만든다.
- CI 러너에는 오디오 장치도 타사 플러그인도 없다. 그쪽은 개발 기계에서 따로 확인하며 결과는 [호환성 표](compatibility-2026-09-10.ko.md)에 있다.
