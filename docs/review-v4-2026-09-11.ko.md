## 발견 사항 (우선순위 순)

### R1 [P1] 늦은 AI 응답의 기준 revision을 현재 값으로 덮어쓴다

Main.cpp::considerSuggestedChange, 약 1122행.
fields->setProperty("base_revision", project.revision)가 응답 도착 시 실행된다. 질문을 revision N에서 보내고 응답 전에 사람이 노트를 수정해 N+1이 되어도 제안이 N+1 기준인 것처럼 등록된다. Tools::createProposal/applyProposal의 revision 검사가 정상이어도 이 경로에서는 오래된 요청임을 구별하지 못한다. '내가 이미 고친 노트'를 AI의 이전 문맥으로 덮어쓸 수 있다.

수정: 전송 시 호스트가 보관한 음악 revision/context snapshot을 사용한다. 모델이 보낸 revision도 신뢰하지 않는다. N과 현재 revision이 다르면 stale 표시/재생성으로 처리한다.
검사: 질문 전송→같은 노트 수동 변경→지연 응답→제안 거절 및 수동 변경 보존. 응답 이후 적용 전 변경뿐 아니라 응답 이전 변경을 반드시 검사.

### R2 [P1] 노트 첨부가 없는 응답도 노트 수정 범위를 스스로 지정할 수 있다

Main.cpp::considerSuggestedChange 약 1090~1118행, Tools.h::readNoteChange 약 570~580행, Proposal.h::allowedNotes.
suggested.clone()으로 모델 필드를 복사한 뒤 notes 첨부가 있을 때만 pattern/channel을 덮어쓴다. Insert만 첨부하거나 노트 첨부가 없는 질문에서는 모델의 pattern/channel이 남는다. allowed_notes는 빈 배열이 되고 서비스는 빈 배열을 '해당 채널의 모든 노트 허용'으로 해석한다. 따라서 유효한 패턴/채널/노트 ID를 지정한 응답은 사용자가 첨부하지 않은 노트 제안을 만들 수 있다. Apply가 필요해도 '첨부한 대상만 수정' 계약 위반이다.

수정: 응답에서 scope 필드를 먼저 제거하고 호스트 첨부로만 구성한다. 노트 쓰기 권한 없음과 전체 파트 권한을 서로 다른 명시적 값으로 표현한다. 노트 첨부가 없으면 notes 작업을 거절한다. 다중 첨부 시 마지막 pattern/channel만 남고 ID 목록은 합쳐지는 경우도 분리 처리한다.
검사: Insert-only/region-only/무첨부에서 notes 제안을 보내 OUT_OF_SCOPE 확인. 정상 노트 첨부와 전체 파트 첨부는 의도한 범위만 허용.

### R3 [P2] 노트 추가의 검증 기본값과 적용 기본값이 다르다

Tools.h::readNoteChange 약 621~629행 및 applyProposal 약 524~533행.
add 노트의 start/length가 생략되면 검증에서는 wasStart/wasLength 초기값 0/0을 사용한다. 적용에서는 0/1을 사용한다. 길이가 1 beat보다 짧은 유효 패턴에 add 요청을 보내 length를 생략하면 검증은 통과하고 패턴 끝을 넘는 노트가 들어갈 수 있다. 설명과 실행 결과가 달라지는 입력이다.

수정: add 필수 필드를 요구하거나 검증 전에 기본값을 한 번 확정해 검증·diff·적용에서 공유한다. 임의 what 문자열을 change로 취급하는 경로와 정수/실수의 강제 캐스팅도 엄격한 입력 검증으로 정리한다.
검사: 0.5 beat 패턴에 length 생략 add 거절 또는 명시적으로 유효한 기본값으로 일관 처리. 잘못된 타입/소수 pitch/알 수 없는 what도 검사.
