ZIP 안의 `BUILD-INFO.json`이 위 커밋과 실행 파일 해시를 들고 다니고, `verification/test-report.json`이 그 해시를 자기가 검사한 대상으로 적는다. 봉인 단계가 둘이 같은지 확인한 뒤에만 해시를 낸다. 즉 이 표의 값들은 서로를 가리키며, 다른 빌드의 보고서로는 이 ZIP을 봉인할 수 없다.

확인 방법은 이렇다.

```
Get-FileHash CoCompose-0.1.0-windows-x64.zip -Algorithm SHA256    # 위 ZIP 해시와 비교
# 압축을 푼 뒤
Get-Content BUILD-INFO.json                                        # commit과 sha256
Get-FileHash CoCompose.exe -Algorithm SHA256                       # BUILD-INFO의 sha256과 비교
Get-Content verification/test-report.json                          # executable_sha256이 같은지
```

## 어디서 무엇을 돌렸는가

같은 커밋에 대해 세 곳의 결과를 따로 적는다. 셋은 보는 것이 다르므로 하나로 합치지 않는다.

### 1. 깨끗한 Windows 환경 (개발 도구가 닿지 않는 PATH)

이 기계에서, 개발 도구가 하나도 없는 PATH로 배포본을 실행했다. 무엇 하나 설치하지 않은 사람이 하는 일과 같다.

| 검사 | 결과 |
|---|---|
| 압축을 푼 실행 파일로 통합 검사 28개 | 통과, 보고서의 대상 해시가 위 실행 파일과 일치 |
| 두 번 누른 것처럼 시작 | 창이 뜨고 이전 프로젝트가 복원됨 |
| `Install.cmd` 설치 | 프로그램 복사, 시작 메뉴 바로가기 생성 |
| 같은 설치 반복(업데이트) | 채널·패턴·노트·BPM 그대로 |
| 실행 중 제거 시도 | 거절(exit 3), 프로그램과 바로가기 그대로 |
| `Uninstall.cmd` 제거 | 프로그램과 바로가기 제거, 프로젝트 보존 |
| 봉인이 잘못된 보고서를 거절 | 8종 모두 거절, 올바른 보고서 하나 통과 |

### 3. CI (GitHub Actions, windows-2022)

러너에는 오디오 장치도 타사 플러그인도 없다. 그래서 CI가 보는 것은 모델·작업 화면·파일 프로토콜·렌더·패키징이다.

순서: 빌드 → 패키징 → ZIP 압축 해제 → 압축 푼 실행 파일로 통합 검사 → 두 번 누른 것처럼 시작 → 설치·업데이트·제거 → 봉인 거절 검사 → 봉인 → 업로드. 앞이 하나라도 실패하면 배포물은 올라가지 않는다.

CI는 자기 기계에서 다시 빌드하므로 실행 파일 해시가 이 문서의 값과 다르다. MSVC 빌드는 비트 단위로 재현되지 않는다. 대신 CI가 만든 ZIP도 같은 규칙으로 봉인되므로, 그 ZIP 안의 `BUILD-INFO.json`과 `verification/test-report.json`이 서로를 가리킨다. 어느 쪽 파일을 손에 들었든 그 파일에 대해 무엇이 돌았는지 알 수 있다.

이 후보의 커밋(`9110648`)에 대한 CI는 통과했다.

gate는 실제로 네 번 나쁜 빌드를 막았다. 렌더용 Edit를 작업 스레드에서 만들어 러너에서 멈춘 빌드, 오디오 장치가 없는 러너에서 걸린 녹음 검사, take를 저장하지 않던 경로, 그리고 화면 크기를 고정값으로 가정한 검사다.

**한 번은 흔들림이었다.** RC1로 삼으려던 커밋(`e928b5c`)에서 러너의 `control(undo)`가 응답받지 못해 실패했는데, 코드가 같고 문서만 더한 커밋(`6ed495f`)은 같은 검사를 두 번 연속 통과했다. 로컬에서도 단독으로 세 번 연속 통과한다. 그래서 그것을 쫓다 찾은 세 가지(재생 중 루프 이동, 스트립 무조건 다시 그리기, 반쯤 쓰인 control 요청을 삼키던 것)는 전부 실제 문제이고 고쳤지만, **그중 무엇이 그 실패의 원인이었는지는 확정하지 못했다.** 부하가 걸린 상태에서만 나타나며 재현이 안정적이지 않다.

## 알려진 제한

기능 실패가 아니라 이 후보가 하지 않기로 한 것, 또는 아직 확인되지 않은 것이다.

### 정책상 하지 않는 것

- **코드 서명 없음.** 처음 실행할 때 SmartScreen 경고가 뜬다. `추가 정보 > 실행`을 눌러야 한다. 대신 해시를 낸다. [배포 방식](release.ko.md)에 이유가 있다.
- **자동 업데이트 없음.** 앱이 네트워크에 나가지 않는다. 새 ZIP을 받아 압축을 풀거나 `Install.cmd`를 다시 실행한다. 프로젝트는 설치 폴더 밖에 있어 그대로 남는다.
- **설치 EXE 없음.** 하는 일이 폴더 복사와 바로가기 생성뿐이라 배치 파일로 충분하다고 판단했다.
- **x64 Windows만.** 다른 플랫폼은 만들지 않는다.

### 기능상의 제한

- 한 번에 한 프로젝트만 연다. 두 번째를 열면 이미 열린 창을 앞으로 가져오고 무엇을 열고 있는지 알린다.
- VST3만, 기본 경로만 스캔한다. VST2·AU는 다루지 않는다.
- 프리셋은 같은 종류의 악기끼리만 오간다. 맞지 않으면 무엇을 위한 것인지 말한다.
- 그래프가 바뀌는 순간 재생이 잠깐 끊길 수 있다. 라이브 싱크는 무결점 오디오를 보장하지 않는다.
- 시작 화면은 없다. 마지막 프로젝트를 바로 연다.

### 아직 확인되지 않은 것

여기 있는 항목은 통과가 아니라 미검증이다.

- **청음.** 렌더된 WAV를 사람이 듣는 것. [수용 검사 기록](acceptance-2026-09-10.ko.md)의 항목이며 아직 비어 있다.
- **실제 플러그인 음색 선택.** 플러그인 창에서 음원을 고른 뒤의 소리와 렌더.
- **MIDI 건반 실물 녹음, 오디오 입력 녹음.** 장치는 이 기계에 붙어 있으므로 "장치 없음"으로 넘길 수 없다.
- **재생 중 장치 전환, 인터페이스 분리.**
- **다른 오디오 인터페이스, ASIO, 다른 샘플레이트·버퍼.**
- **무음으로 렌더된 악기의 원인.** 라이브러리를 불러와야 소리가 난다고 적었지만 아직 추정이다.

## 판정

**RC2로 지정한다.** RC1(`e928b5c`)은 CI가 한 번 흔들린 뒤 같은 코드로 두 번 통과했지만, 그 사이에 찾은 세 가지를 고치면서 바이너리가 바뀌었으므로 후보를 다시 잘랐다. 위 표의 커밋·해시·검사 결과가 서로를 가리키고, 개발 도구 없이 설치·업데이트·제거가 되며 프로젝트가 세 단계 모두에서 보존된다.

정식 릴리스로 올리려면 "아직 확인되지 않은 것"의 청음과 실장치 항목이 채워져야 한다. 그것은 사람이 하는 일이고, 그때까지 이 후보는 후보로 둔다.
