# 공동 작곡 편집기 작업 기록

## 2026-09-07 — CoCompose 첫 구현

대상은 기존 DAW·VST 사용자다. 목표는 외부 AI와 함께 작곡하는 것이며 앱 내 채팅은 뒤로 미뤘다. 필수 조건인 라이브 싱크는 열린 `Edit`를 유지하면서 데이터와 UI를 갱신하는 방식으로 구현한다.

### 작업 단위

### 구현 선택과 범위

별도 MCP 서버나 앱 내 모델 공급자 연결보다 JSON 파일 경로를 먼저 만들었다. 외부 도구가 최신 실제 상태를 읽고 수정한 뒤 결과를 확인할 수 있다. MIDI 트랙·클립·노트는 안정적인 ID로 찾고 갱신하며, 배열에서 빠진 항목은 삭제한다. 트랙 gain/mute/solo, BPM 및 이미 존재하는 플러그인의 공개 파라미터를 지원한다.

네이티브 프로젝트 로드는 앱 시작 시 한 번 수행한다. 라이브 변경 때 프로젝트를 다시 열거나 Edit 전체를 교체하지 않는다. 유효하지 않은 요청은 수정 전에 거절하고, 적용 중 예외는 현재 undo transaction으로 되돌린다. UI와 외부 도구의 경쟁 편집은 session ID와 revision으로 검출한다.

입력용 `project.json`은 초기 생성 후 앱이 덮어쓰지 않는다. 모든 후속 수정은 최신 `state.json`에서 시작한다. 요청 ID로 제출과 결과를 연결하며, 제어 요청은 `control.json`과 `control-status.json`을 사용한다. 파일 저장 실패는 `applied_unpersisted`로 구분한다. VST의 공개 파라미터 밖 내부 상태는 약 2초마다 flush와 서명 비교로 감지한다. 해당 경로의 타사 플러그인 호환성은 미검증이다.

현재 구현은 C++ 바이너리 자체의 핫 리로드, 완성형 피아노롤, 앱 내 채팅, WAV 렌더/A-B 평가를 포함하지 않는다. 서드파티 VST 호스팅 활성화와 실제 플러그인 호환성 검증도 구분한다.

### 검증 기록

CoCompose Windows Release 빌드가 MSVC 19.44.35223에서 성공했다. `tools/test_live_sync.py`를 실제 Release 실행 파일에 대해 실행하여 아래 10개 검사를 모두 통과했고 종료 코드는 0이었다. 테스트 결과 파일도 문서 담당 에이전트가 읽어 확인했다.

1. Windows 앱 시작과 실제 Tracktion 재생 상태.
2. 동일 session/Edit 인스턴스에서 템포·트랙 이름·음높이·velocity 변경 및 실제 UI 라벨 변경.
3. 유효하지 않은 MIDI를 이전 상태 변경 없이 거절.
4. 저장 중인 불완전 JSON을 이전 상태 변경 없이 거절.
5. 오래된 revision과 다른 session 요청 거절.
6. 노트 전체 비우기, 한 번의 Undo 복원, Redo 재적용.
7. 내장 신스 필터 파라미터 실제 엔진 readback 및 Undo.
8. 트랙 추가·순서 변경·삭제 중 같은 Edit 유지.
9. state 출력 경로 차단 시 `applied_unpersisted` 구분 및 경로 복구 후 자동 저장.
10. 정상 종료 후 재실행 시 음악과 내장 플러그인 상태 보존. 부동소수점 비교 허용 오차는 `1e-8`.

검증 산출물은 `build-cocompose/live-test-a66d5569/`의 `test-report.json`, `before.png`, `after.png`, `ui-state.json`이다. 이 폴더는 로컬 빌드 산출물이므로 다른 checkout에는 없을 수 있다. 재현 명령은 저장소 루트에서 `python tools/test_live_sync.py`다. 기존 앱은 먼저 정상 종료한다.

라이브 검사에서는 session/Edit 유지 여부를 확인했고, 마지막 검사의 종료·재실행은 저장 복원 검증을 위해 별도로 수행했다. 음악 변경 때 프로젝트를 다시 열도록 요구하지 않는다.

실제 오디오 청취와 외부 VST3 호환성은 미검증이다. 재생 그래프 변경으로 엔진의 재생 플래그가 꺼지면 사용자의 재생 의도를 유지해 다음 UI tick에서 재개한다. 앱·프로젝트를 다시 열 필요는 없지만 무중단 음향을 보장하지 않는다.

### Windows ZIP 배포 작업

`tools/build-windows.ps1`에 Visual Studio 2022용 CMake Release 빌드와 CPack ZIP 생성을 연결했다. 출력은 `build-cocompose/dist/CoCompose-0.1.0-windows-x64.zip`이며 로컬 패키지 검증은 진행 중이다. 기존 Release 앱의 통합 검사 성공이 ZIP 배포 검사까지 의미하는 것은 아니다.

`.github/workflows/cocompose-windows.yml`에 Windows 빌드·artifact 업로드를 추가했다. 관련 경로의 `ai-editor` push, 해당 브랜치 대상 PR, 수동 실행을 지원한다. 원격 CI 실행 성공 여부는 아직 확인하지 않았다.

ZIP을 모두 풀어 `CoCompose.exe`를 더블클릭하는 사용법을 문서에 반영했다. 일반 실행에는 PowerShell·Python·Visual Studio가 필요 없다. 기본 프로젝트는 문서 폴더에 저장되므로 새 배포 폴더와 분리된다. `docs/windows-portable.ko.txt`가 배포용 안내다. 현재 코드 서명·설치 프로그램·자동 업데이트는 포함하지 않는다.

## 2026-09-10 — M0 인수·빌드·배포 기준선 확정

`docs/claude-handoff-milestones.ko.md`의 M0 완료 조건을 검증했다. 인수 시점의 미커밋 배포 작업은 덮어쓰지 않고 검토 후 `2e45b25`로 커밋했다.

### ZIP 배포 EXE 검증

로컬 `build-cocompose/dist/CoCompose-0.1.0-windows-x64.zip`의 내용은 `CoCompose.exe`, `README.txt`, `licenses/`, `tools/`이며 EXE가 압축 해제 폴더 바로 아래에 있다. ZIP 안의 EXE는 `build-cocompose/CoCompose_artefacts/Release/CoCompose.exe`와 SHA-256이 같다.

`python tools/test_live_sync.py --exe <압축 해제한 CoCompose.exe>`를 ZIP EXE에 대해 실행해 기존 10개 통합 검사를 모두 통과했고 종료 코드는 0이었다. 검사 항목은 위 2026-09-07 기록과 같다.

### Windows CI 검증

`.github/workflows/cocompose-windows.yml`이 `ai-editor` push에서 실행되어 성공했다. run 34420462358, 약 9분, 커밋 `2e45b25`. `CoCompose-windows-x64` artifact를 다운로드해 압축을 풀었고 ZIP 구조와 EXE 버전 정보(0.1.0)가 로컬 패키지와 일치했다.

CI artifact의 EXE에 대해서도 `tools/test_live_sync.py`를 실행해 10개 검사를 모두 통과했다. 원격 빌드 산출물이 로컬 빌드와 동일하게 동작함을 확인했다.

### 개발 도구 없는 환경 시작 검사

`tools/test_portable_start.ps1`을 추가했다. PATH를 Windows 기본 디렉터리만 남기고 `cmake`, `python`, `cl`, `git`, `msbuild`가 실제로 도달 불가능한지 확인한 뒤, 인자 없이 EXE를 실행한다. 더블클릭과 같은 경로다.

로컬 ZIP EXE와 CI artifact EXE 모두 창(`CoCompose`)이 뜨고, 문서 폴더의 기존 프로젝트가 그대로 복원되었다. 트랙 1개, 노트 32개, BPM 120, 트랙 이름 `CoCompose Synth`가 실행 전후로 동일했고 `state.json`이 갱신되었다. 새 예제 프로젝트로 덮어쓰지 않는다.

### 남은 제한

실제 청음과 타사 VST3 호환성은 여전히 미검증이다. 코드 서명·설치 프로그램·자동 업데이트는 없다. 검사는 개발 도구가 설치된 장비에서 PATH를 제한해 수행한 것이며, 완전히 새로 설치한 Windows 장비에서의 검사는 아니다.

## 2026-09-10 — M1 작업 공간과 패턴 중심 데이터 모델

`docs/claude-handoff-milestones.ko.md`의 M1을 구현했다. 화면을 흉내 내는 대신 각 패널의 컨트롤이 모델을 거쳐 실제 엔진에 도달하도록 만들었다.

### 데이터 모델

Edit 안의 `COCOMPOSE` 트리에 Channel, Pattern, Playlist lane, Clip instance, Mixer insert를 서로 다른 객체로 둔다. 하나의 engine audio track에 모두 묶지 않는다. Channel 하나가 engine audio track 하나를 소유하고, Pattern은 채널별 `SEQUENCE`로 노트를 담는다. Clip instance는 패턴을 레인의 특정 박에 배치한 참조다.

엔진 MIDI 클립은 이 모델에서 파생시킨다. (배치, 그 패턴에서 연주하는 채널) 쌍마다 클립 하나를 만들고 클립 상태에 두 ID를 기록해 다시 찾는다. 그래서 패턴을 고치면 그 패턴의 모든 배치가 함께 바뀐다. 파생 클립 자체는 Undo 대상이 아니다. Undo는 모델을 되돌리고 다음 tick에서 엔진을 다시 파생시키므로 한 편집이 한 Undo로 유지된다.

Mixer insert는 모델과 저장까지만 구현했다. 실제 라우팅은 M5다. 현재 오디오는 각 채널에서 Master로 직결된다.

### 변환

`COCOMPOSE` 트리가 없는 세션을 열면 트랙마다 채널과 전용 레인을, MIDI 클립마다 패턴과 배치 하나를 만든다. 기존 클립을 지우고 다시 만들지 않고 배치 ID를 붙여 그대로 인수하므로 편곡과 플러그인 상태가 그대로 남는다. 트랙·클립·노트의 `coComposeId`를 각각 채널·패턴·노트 ID로 재사용한다.

schema 1 JSON 입력도 같은 규칙으로 schema 2로 올린 뒤 적용한다. 두 경로 모두 ID가 같으므로 기존 외부 스크립트의 참조가 유지된다.

`tests/cocompose/legacy-schema1.tracktionedit`는 패턴 도입 이전 빌드가 저장한 실제 세션이며 변환 검사에 사용한다.

### 화면

Browser(왼쪽), Channel Rack(가운데 위), Mixer(가운데 아래), Pattern picker와 Playlist(오른쪽)를 배치했다. 패널 사이 막대로 크기를 조절하고 View 메뉴 또는 `Alt+1`~`Alt+5`로 숨기거나 되살린다. 포커스된 패널은 테두리로 표시하며 `F6`으로 순환한다. 패널 크기·표시 여부·선택은 Edit의 `COCOMPOSELAYOUT`에 저장되어 다시 열 때 복원된다. 선택은 편집이 아니므로 Undo 대상이 아니다.

각 패널은 실제 데이터를 보여준다. Browser는 프로젝트의 채널·패턴·레인·인서트와 스캔된 플러그인을, Channel Rack은 채널별 이름·mute/solo·볼륨·인서트 번호·악기 창과 선택 패턴에서의 노트 수를, Mixer는 Master와 인서트별 볼륨·팬·mute 및 배정된 채널 수를, Pattern picker는 패턴과 배치 횟수를, Playlist는 레인과 배치 개수 및 파생된 클립이 보이는 타임라인을 보여준다.

상단에 File/Edit/View/Tools/Help 메뉴와 재생·Song/Pattern·BPM·마디:박·메트로놈·CPU·포커스 표시를 붙였다. 모든 메뉴 항목은 `ApplicationCommandManager`에 연결되어 있고 동작하지 않는 항목은 두지 않았다. Song 모드는 편곡 전체를, Pattern 모드는 선택한 패턴의 첫 배치를 반복한다.

### 검증

`tools/test_live_sync.py`가 15개로 늘었고 전부 통과했다. 기존 10개 항목을 새 모델로 옮기면서 각 항목에 `state.json`의 읽기 전용 `engine` 결과 확인을 추가해, 모델만 바뀌고 엔진에는 도달하지 않는 통과를 막았다.

추가된 검사는 다음 다섯 가지다.

11. 한 패턴을 두 곳에 배치하고 패턴을 수정하면 두 배치의 엔진 클립이 함께 바뀌며 Undo 한 번으로 둘 다 복원된다.
12. 배치 하나에 패턴 복제본을 연결하면 그 배치만 바뀌고 원래 패턴은 그대로다.
13. 패턴 도입 이전 세션이 채널·패턴·플레이리스트로 변환되며 ID와 노트가 유지된다.
14. schema 1 `project.json` 입력이 패턴 모델로 올라간다.
15. 패널 크기·표시 여부·선택이 세션에 저장되고, 수정한 값이 다음 실행에서 그대로 복원된다.

화면은 실행 중인 앱의 스크린샷으로도 확인했다. 외부에서 채널·시퀀스·배치를 추가하면 Browser, Channel Rack, Mixer, Pattern picker, Playlist가 앱을 다시 열지 않고 갱신된다.

### 남은 제한

패널 크기 조절 막대를 마우스로 끄는 동작 자체는 자동 검사가 아니다. 저장된 크기를 앱이 존중하는지까지만 검사한다. 스텝 시퀀서·피아노롤(M2), 마우스 플레이리스트 편집(M3), 샘플 브라우저(M4), 믹서 라우팅과 효과(M5)는 아직 없다. Playlist 타임라인은 Tracktion 예제 컴포넌트이며 레인이 아니라 채널 단위로 클립을 보여준다. 실제 청음과 타사 VST3 호환성은 여전히 미검증이다.

## 2026-09-10 — M2 Channel Rack과 피아노롤

`docs/claude-handoff-milestones.ko.md`의 M2를 구현했다.

### 채널

채널마다 악기를 고른다. 내장 4OSC, 내장 샘플러, 스캔된 VST3 악기가 선택지이며 모델의 `instrument` 값이 곧 트랙 첫 플러그인의 종류다. 값이 바뀌면 `render()`가 기존 악기를 교체하고, 만들 수 없는 플러그인이면 요청을 모델에 남긴 채 교체하지 않는다. 나중에 스캔하면 그때 붙는다.

샘플러는 `sample` 경로의 파일 하나를 채널의 `step_pitch`를 기준음으로 건반 전체에 배치한다. 채널 행의 `WAV` 버튼이 파일을 고르고 악기를 샘플러로 바꾼다.

행에는 이름, mute/solo, 악기 선택, 악기 창 열기, 샘플 선택, 볼륨·팬 노브, 믹서 인서트 번호가 들어간다. 나머지 공간은 스텝 그리드가 차지한다.

### 스텝 그리드

선택한 패턴을 16분음표 단위로 나눈 격자다. 스텝 하나는 그 구간에서 시작하는 노트가 있는지로 결정한다. 누르면 채널의 `step_pitch`·`step_length`로 노트를 쓰고, 켜진 스텝을 누르면 지운다. 두 값은 채널 행의 스텝 설정 버튼에서 1/16~1마디 길이와 기준음으로 고른다. 끌면 여러 스텝을 연속으로 바꾼다. 새 패턴의 기본 길이는 한 마디(4박, 16스텝)로 맞췄다.

### 피아노롤

`Piano roll` 버튼이 선택한 채널·패턴의 노트 편집기를 별도 창으로 연다. 추가·삭제·이동·길이 조절·velocity 조절, 사각형 다중 선택, 복제, 퀀타이즈, 스냅(1/1~1/16, off), 확대를 제공한다. 왼쪽 건반을 누르면 `playGuideNote`로 채널의 실제 악기를 통해 미리듣는다. 아래쪽 VELOCITY 칸은 그리드와 가로 스크롤을 공유하며 노트별 세기를 보여준다. 열 때 노트가 있는 음역으로 스크롤한다.

노트는 모델의 `NOTE`이므로 스텝이든 피아노롤이든 편집은 그 패턴의 모든 배치에 반영되고 Undo 한 번으로 함께 되돌아간다. 외부 편집과 같은 경로다.

### 화면 조작 재생 (`--ui-script`)

화면이 실제로 동작하는지 외부에서 검사하기 위해 `--ui-script <파일>`을 추가했다. JSON 배열의 조작을 250ms마다 실제 패널에 재생하고 `ui-script-status.json`에 진행 상황을 남긴다. 지원 항목은 메뉴 명령 이름, 채널·패턴·레인 선택, 스텝 토글, 피아노롤 노트 추가다. 모델을 직접 건드리지 않고 화면과 같은 코드 경로를 지나간다. `--screenshots`와 같은 진단 기능이며 라이브 싱크 규약의 일부가 아니다.

`--screenshots`는 피아노롤이 열려 있으면 `piano-roll.png`도 남긴다.

### schema

채널에 `instrument`, `sample`, `step_pitch`, `step_length`를 추가했다. 기존 schema 2 문서에 없어도 되는 선택 필드이므로 버전은 올리지 않았다. 값이 비어 있으면 4OSC로 정규화한다.

### 검증

`tools/test_live_sync.py`가 16개로 늘었고 전부 통과했다. 새 검사는 M2의 완료 조건이다. `--ui-script`로 메뉴 명령·스텝 그리드·피아노롤만 사용해 드럼 6스텝, 베이스 4스텝, 멜로디 5노트의 3채널 패턴을 만들고, 배치·재생·저장까지 진행한 뒤 다음을 확인한다.

- 세 채널의 노트가 모델과 엔진 클립 3개에 정확히 들어간다.
- 재생이 실제로 시작된다.
- 외부에서 멜로디를 반음 3개 올리면 열려 있는 편집기의 모델과 엔진 클립에 반영된다.
- 종료 후 다시 열면 채널·패턴·엔진 클립이 그대로 복원된다.
- 화면 라벨에 세 채널 이름이 모두 나타난다.

피아노롤 화면은 `piano-roll.png` 스냅샷으로도 확인했다.

### 남은 제한

샘플러는 사운드 하나만 다루며 다중 존·루프·스트레치는 없다. 마우스 드래그 자체는 자동 검사 대상이 아니고 `--ui-script`가 같은 코드 경로를 호출하는 것까지 검사한다. 마우스 플레이리스트 편집(M3), 샘플 브라우저(M4), 믹서 라우팅과 효과(M5)는 아직 없다. 실제 청음과 타사 VST3 호환성은 여전히 미검증이다.

## 2026-09-10 — M3 Playlist와 Pattern picker

### 클립의 의미 확장

배치에 `offset`을 더했다. 클립은 패턴을 `offset` 지점부터 `length` 만큼 보여주며, 패턴보다 길면 반복한다. 이 규칙 하나로 분할과 반복이 모두 나온다. 분할은 앞 조각의 길이를 줄이고 뒤 조각의 `offset`을 잘린 만큼 늘린 복사본을 만든다. 소리는 이어지고 배치만 둘로 나뉜다.

`syncClip`이 이 규칙대로 엔진 클립의 노트를 만든다. 반복 횟수만큼 패턴 노트를 밀어 넣고, 클립 경계에 걸친 노트는 보이는 부분만 남긴다. 노트 식별자에 반복 번호를 붙여 구분한다.

### 편곡 격자

`PlaylistGrid`가 기존 Tracktion 예제 타임라인을 대신한다. 가로는 박, 세로는 레인이며 마디 눈금, 재생 커서, 루프 범위를 그린다. 클립은 패턴마다 다른 색이고, 반복이 다시 시작하는 지점에 세로선을 넣는다.

조작은 배치, 이동(마디·레인 동시), 크기 조절, Ctrl 복사, 오른쪽 버튼 삭제, Alt 사각형 선택, 더블클릭 분할, `Ctrl+E` 재생 커서 분할, `Ctrl+R` 복제, `Ctrl+U` 독립화, `Delete` 삭제다. 눈금자를 끌면 루프 범위를 정하고 Ctrl+휠로 확대한다. Snap은 마디부터 1/8까지와 끄기를 고른다.

Pattern picker의 패턴을 끌어다 레인에 놓을 수 있다. Workspace가 `DragAndDropContainer`이고 picker의 목록이 패턴 ID를 드래그 소스로 내놓는다.

레인 추가·삭제·mute는 Playlist 패널 아래 버튼에 있다. 레인을 지우면 그 레인의 배치도 같은 Undo로 함께 사라진다.

`Selection`과 레이아웃 식별자는 `PlaylistGrid`가 참조해야 해서 `Model.h`로 옮겼다.

### 화면 조작 재생 확장

`--ui-script`에 `place`, `pick_clip`, `move_clip`, `split_clip`을 더했다. 그리고 스크립트 파일이 바뀌면 다시 읽어 회차를 올리도록 바꿨다. 앱을 다시 띄우지 않고 한 세션에서 여러 단계를 검사할 수 있다. 재생을 유지한 채 편집하는 조건을 확인하려면 필요한 변경이다.

### 검증

`tools/test_live_sync.py`가 17개로 늘었고 전부 통과했다. 새 검사가 M3의 완료 조건이다. 재생 중인 한 세션에서 다음을 수행한다.

1. 4마디 패턴을 스텝 그리드로 만들고 길이를 16박으로 맞춘다.
2. 격자에 8번 배치해 32마디를 만든다. 배치 8개가 모두 엔진 클립이 되고 재생이 계속된다.
3. 마지막 클립을 한 마디 뒤로 옮긴다. 엔진 클립의 시작 위치가 따라온다.
4. 그 클립을 반으로 자른다. 두 조각의 길이가 각각 8박이고 뒤 조각의 `offset`이 8이며, 두 조각의 엔진 노트 수를 합치면 원래와 같다. 뒤 조각의 노트는 모두 조각 안에 들어 있다.
5. Undo 한 번으로 클립이 다시 하나가 되고 엔진 클립의 노트도 원래대로 돌아온다.
6. 클립 복제가 바로 뒤에 하나를 더한다.
7. 재생 중에 외부에서 배치를 추가하면 엔진에 반영되고, session ID가 그대로이며 재생도 멈추지 않는다.

3레인 편곡 화면은 스크린샷으로도 확인했다.

### 남은 제한

레인 이름 바꾸기는 아직 외부 편집으로만 한다. 격자에는 시간 표시가 마디 단위만 있고 박자표는 4/4 고정이다. 오디오 클립과 자동화 클립은 없다(M4, M6). 샘플 브라우저(M4), 믹서 라우팅과 효과(M5)는 아직 없다. 실제 청음과 타사 VST3 호환성은 여전히 미검증이다.

## 2026-09-10 — M4 Browser와 오디오 클립

### 오디오 클립

플레이리스트의 `CLIPS` 아래에 `AUDIO` 항목을 더했다. 패턴 배치와 같은 부모를 공유하되 종류가 다르다. 파일 경로, 시작·길이·파일 안에서의 오프셋, 게인, 페이드 인/아웃, 속도를 갖는다.

악기 채널은 트랙을 소유하지만 오디오는 채널에 속하지 않는다. 그래서 오디오를 가진 레인이 `lane:<id>` 태그의 엔진 트랙을 하나 갖는다. 트랙은 그 레인에 오디오가 있을 때만 만들어지고 없어지면 사라진다. 클립은 다른 파생물처럼 `syncClips`가 만들고 지운다.

`applyList`가 부모 안에서 자기 종류만 교체·정렬하도록 바꿨다. 덕분에 한 트리에 패턴 배치와 오디오 클립이 함께 있어도 서로를 지우지 않는다.

### 편집

Playlist 격자가 오디오 클립을 파형과 함께 그린다. 페이드는 실제로 적용되는 모양대로 삼각형으로 표시하고, 반복 경계 대신 파일 위치를 보여준다. 파일이 없으면 클립이 붉게 바뀌고 이름 대신 `missing`을 표시한다.

이동·크기 조절·분할·복제·삭제는 패턴 클립과 같은 코드가 처리한다. 분할은 뒤 조각의 오프셋을 늘리는 같은 규칙이라 오디오에서도 소리가 이어진다. 게인·페이드·속도·오프셋은 `shapeSelection`으로 바꾼다.

탐색기에서 직접 끌어놓는 것과 Browser에서 끌어놓는 것을 모두 받는다.

### Browser

프로젝트 자산(채널·패턴·레인·인서트·사용 중인 샘플), 등록한 폴더 트리, 즐겨찾기, 최근 미리듣기, 스캔된 플러그인을 한 목록에 보여준다. 폴더는 누를 때만 펼쳐지므로 큰 라이브러리도 비용이 없다. 검색은 이름 부분 일치다.

미리듣기는 Edit를 건드리지 않고 기본 출력 장치로 직접 재생한다. 폴더·즐겨찾기·최근 목록은 Edit의 `COCOMPOSEBROWSER`에 저장되어 다시 열 때 그대로다.

`Find`는 누락된 샘플 하나를 찾아주면 같은 폴더에서 나머지 누락 파일도 함께 다시 연결한다. 프로젝트를 다른 기기로 옮겼을 때의 실제 상황에 맞춘 동작이다.

### 자산 수집

`File > Collect samples`가 쓰이는 샘플을 세션 옆 `samples` 폴더로 복사하고 클립이 사본을 가리키게 한 뒤 저장한다. 이름이 겹치고 크기가 다르면 번호를 붙인다.

### 검증

`tools/test_live_sync.py`가 18개로 늘었고 전부 통과했다. 새 검사가 M4의 완료 조건이다. 검사는 자체적으로 짧은 WAV를 만들어 쓰므로 샘플 라이브러리가 필요 없다.

1. WAV를 레인에 놓으면 모델과 엔진 양쪽에 오디오 클립이 생긴다.
2. 길이·오프셋·게인·페이드 인/아웃·속도를 바꾸면 엔진 readback에 그대로 나타난다.
3. 오디오가 아닌 파일을 가리키는 요청은 프로젝트를 바꾸기 전에 거절되고, 기존 클립은 계속 재생된다.
4. 파일을 옮기면 `missing`으로 바뀌고, 되돌리면 다시 재생된다.
5. 자산 수집이 파일을 `samples` 폴더로 옮기고 클립이 계속 재생된다.
6. 폴더를 통째로 복사해 원본 샘플을 지운 뒤 열어도 오디오가 살아 있다.

## 2026-09-10 — M5 Mixer와 효과 체인

`docs/claude-handoff-milestones.ko.md`의 M5를 구현했다.

### 조사 결과와 직접 만든 것

필요한 여섯 효과 중 다섯은 엔진에 있었다. EQ는 `4bandEq`, limiter는 `compressor`, delay·chorus·reverb는 같은 이름의 내장 플러그인이다. saturation만 없어서 `examples/CoCompose/Saturation.h`에 만들었다. drive로 tanh 곡선에 밀어 넣고 wet/dry로 섞은 뒤 출력 게인을 거는 구조이며, drive를 올려도 레벨이 크게 변하지 않도록 `tanh(drive)`로 정규화한다. AirWindows 라이브러리 전체를 켜지 않기 위한 선택이다.

센드는 엔진의 `AuxSendPlugin`/`AuxReturnPlugin`을 쓴다.

### 라우팅

인서트가 실제 버스 트랙이 되었다. 인서트마다 `insert:<id>` 태그의 엔진 트랙이 있고, 채널 트랙은 자기 인서트 번호의 버스로 출력한다. 오디오 레인은 1번 인서트로 간다. 인서트는 `output`이 가리키는 인서트로, 없으면 기본 장치(Master)로 나간다.

`wouldFeedBack`이 출력 사슬을 따라가 자기 자신으로 돌아오는지 검사한다. 되돌아오는 라우팅과 센드는 모델에 남더라도 엔진에 연결하지 않고, JSON 요청은 적용 전에 거절한다.

### 효과 체인

인서트의 `EFFECT` 자식이 순서대로 트랙의 플러그인이 된다. 종류가 그대로면 기존 플러그인을 두고 자리만 옮기므로 순서를 바꿔도 설정이 살아 있다. 종류가 바뀌면 교체하고, 목록에서 빠지면 지운다. bypass는 플러그인 enable, `wet`은 그 효과에 wet 또는 mix 파라미터가 있을 때 적용한다.

효과의 공개 파라미터는 `state.json`에 나오고 외부에서 바꿀 수 있으며 Undo가 엔진 readback으로 확인된다.

### Undo 정리

작업 중 두 가지 문제를 고쳤다.

렌더는 변경이 있을 때만 쓰도록 바꿨다. 매번 같은 값을 다시 쓰면 호출자의 Undo 트랜잭션에 무의미한 기록이 쌓인다.

그래도 엔진 자체가 플러그인 상태를 Edit에 접어 넣는 기록을 남긴다. 저장 경로는 `Edit::UndoTransactionInhibitor`로 막았고, 그 밖의 기록은 이름 없는 트랜잭션으로 남으므로 Undo/Redo가 이름 없는 트랜잭션을 건너뛰고 사람이 한 편집을 되돌리도록 했다. 앱의 모든 편집은 이름 있는 트랜잭션으로 시작한다.

내장 saturation 타입 등록은 Edit를 여는 `Project` 생성자 첫머리로 옮겼다. 세션에 그 플러그인이 들어 있으면 복원 전에 타입이 있어야 한다.

### 화면

믹서 스트립에 실제 레벨 미터를 붙였다. `LevelMeasurer::Client`를 해당 트랙의 미터 플러그인에 등록하고 프레임마다 읽으며, 값이 떨어질 때는 서서히 내려온다. 스트립에는 이름(편집 가능), 미터, 페이더, 팬, mute, `FX` 메뉴, 체인 요약, 출력 라우팅 버튼, 배정된 채널·센드 수가 있다.

`FX` 메뉴는 효과 추가, 각 효과의 열기·bypass·위아래 이동·삭제, 그리고 다른 인서트로의 센드 추가를 제공한다. 되먹임이 되는 대상은 비활성으로 표시한다.

### 검증

`tools/test_live_sync.py`가 19개로 늘었고 전부 통과했다. 새 검사가 M5의 완료 조건이다.

1. 채널 3개가 각자의 인서트를 거쳐 Master에 도달한다.
2. 드럼 인서트를 드럼 bus로 돌리고 bus가 reverb 인서트로 센드한다. 엔진 트랙의 출력 대상과 `auxsend`/`auxreturn` 플러그인으로 확인한다.
3. 여섯 효과가 실제 엔진 플러그인으로, 모델 순서대로 붙는다.
4. saturation의 drive를 외부에서 바꾸면 엔진 readback에 반영되고 Undo로 되돌아온다.
5. bypass가 플러그인을 지우지 않고 끈다.
6. 자기 자신으로 가는 라우팅은 프로젝트를 바꾸기 전에 거절된다.
7. 체인 순서를 바꾸면 엔진 플러그인 순서도 따라오고 플러그인은 다시 만들어지지 않는다.

화면은 스크린샷으로도 확인했다. 드럼 bus와 reverb 스트립의 미터에 신호가 들어오는 것이 보인다.

인서트의 입력 선택은 채널 배정과 라우팅으로만 하며 장치 입력 선택은 M6이다. 녹음 준비도 M6이다. 채널 EQ 전용 UI는 없고 인서트 체인의 EQ를 쓴다. wet/dry는 효과가 해당 파라미터를 노출할 때만 동작한다. 실제 청음과 타사 VST3 호환성은 여전히 미검증이다.

## 2026-09-10 — M6 자동화, 녹음, 출력

### 자동화

모델의 `AUTOMATION` 아래에 파라미터별 곡선을 둔다. 곡선은 플러그인을 가진 채널 또는 인서트를 `source`로, 그 안의 `plugin_id`와 `parameter`를 가리키고 점 목록을 갖는다. 점은 박 단위 시간, 0–1로 정규화한 값, 곡선 모양이다.

엔진 자동화는 여기서 다시 만든다. 점 목록의 서명이 바뀌었을 때만 엔진 곡선을 지우고 다시 채우므로 재생 중에도 불필요한 재구성이 없다. 사람이 만들든 외부에서 만들든 같은 데이터를 고치고 같은 Undo를 쓴다.

작업 중 실제 문제를 하나 발견해 고쳤다. 자동화가 걸리면 재생 중 파라미터가 계속 움직이고, 그 값이 플러그인 상태에 접혀 들어가면서 플러그인 서명 검사가 2초마다 변화를 보고했다. 그때마다 revision이 올라 외부 편집이 계속 revision 충돌로 거절됐다. 서명 검사는 원래 플러그인 창에서 손으로 돌린 값을 잡기 위한 것이므로 재생 중에는 하지 않도록 했다.

우선권은 이렇게 정했다. 곡선이 있는 파라미터는 재생 중 곡선이 값을 정한다. 값을 바꾸려면 사람이든 AI든 곡선의 점을 고친다. 곡선이 없는 파라미터는 마지막으로 쓴 값을 유지한다.

### 녹음

`Recorder`가 채널을 arm하면 사용 가능한 입력 장치를 그 채널의 트랙에 연결하고 녹음을 켠다. 한 마디 count-in을 선택할 수 있다.

멈출 때 트랙에 남은, 우리 태그가 없는 클립을 모델이 가져간다. MIDI 클립은 새 패턴이 되어 연주한 위치에 배치되고 원본 클립은 지워진다. 오디오 클립은 오디오 클립 모델 항목이 된다. 그래서 녹음 결과도 파생 클립 규칙 안으로 들어와 이동·분할·복제가 된다.

### 출력

`Exporter`가 편곡 전체 또는 루프 구간을 24비트 WAV로 쓴다. 스템은 채널마다 파일 하나씩이며, 그 채널의 인서트와 출력 경로를 따라가며 필요한 버스를 함께 렌더한다. 그렇게 하지 않으면 채널 트랙만 렌더돼 무음이 나온다.

렌더는 별도 스레드에서 돈다. Tracktion의 렌더는 재생 그래프를 가져가고 오디오 장치가 멈추기를 기다리는데, 메시지 스레드에서 부르면 그 대기가 끝나지 않는다. 진행 상황은 `render-status.json`에 남긴다.

### 검증

`tools/test_live_sync.py`가 20개로 늘었고 전부 통과했다. 새 검사가 M6의 완료 조건이다.

1. 필터 곡선의 점 4개가 모델과 엔진 양쪽에 들어간다.
2. 외부에서 점을 추가하면 같은 곡선과 같은 엔진 파라미터에 반영되고 Undo 한 번으로 사라진다.
3. 없는 파라미터를 가리키는 곡선은 프로젝트를 바꾸기 전에 거절된다.
4. 채널 arm/disarm이 모델에 반영된다.
5. 믹스 WAV가 10초를 넘고, 무음이 아니며, 클리핑하지 않는다.
6. 스템이 채널 수만큼 나오고 각각 실제 오디오다.
7. 곡선을 최저값으로 평평하게 만들고 다시 렌더하면 RMS가 낮아진다. 자동화가 소리에 실제로 반영된다는 뜻이다.
8. 다시 열면 곡선이 엔진 자동화까지 복원된다.

검사 도구도 두 곳 고쳤다. 스크립트 동작 뒤 상태가 안정될 때까지 기다리도록 했고, Windows에서 앱이 파일을 열고 있을 때 원자적 교체가 잠깐 거부되는 경우를 재시도하도록 했다.

### 남은 제한

MIDI learn과 하드웨어 컨트롤 서피스 연결은 없다. 자동화 곡선을 화면에서 그리는 편집기는 없고 외부 편집과 `--ui-script`로 만든다. 실제 입력 장치를 연결한 녹음은 이 환경에 장치가 없어 검사하지 못했고, 녹음 결과를 모델이 가져가는 경로까지만 검사했다. 실제 청음과 타사 VST3 호환성은 여전히 미검증이다.

### 프로토콜 유지

별도의 patch/command 계층은 만들지 않았다. schema 2 문서가 이미 채널·패턴·배치·오디오·믹서·자동화를 모두 담고 있고, 전체 스냅샷을 읽어 고쳐 쓰는 규칙 하나로 모든 편집이 표현된다. 명령 계층을 더하면 두 벌의 규칙을 유지해야 하므로 필요해질 때까지 미룬다.

### 적용 결과 diff

`sync-status.json`에 `change`를 추가했다. 적용 직전과 직후의 스냅샷을 비교해 섹션별로 추가·삭제·변경된 ID와 템포 변경 여부를 남긴다. 입력 파일의 되풀이가 아니라 엔진에서 읽어낸 결과다. 외부 도구가 "내가 쓴 대로 됐다"가 아니라 "실제로 이렇게 바뀌었다"를 확인할 수 있다.

`tools/cocompose.py`에 `Conflict` 예외와 `apply_change`를 더했다. 최신 상태를 읽어 수정 함수를 적용하고 제출하며, revision 충돌이나 session 변경이면 처음부터 다시 읽어 새 상태 위에 수정을 다시 얹는다. 오래된 스냅샷을 강제로 덮어쓰는 경로는 만들지 않았다.

Windows에서 앱이 `project.json`을 읽는 중 원자적 교체가 잠깐 거부되는 경우가 있어 helper의 쓰기에도 재시도를 넣었다.

### 검증

`tools/test_live_sync.py`가 21개로 늘었고 전부 통과했다. 새 검사가 M7의 완료 조건이다. 재생 중인 32마디 곡에서 외부 에이전트가 네 가지 작업을 수행한다.

1. 드럼 변형. 패턴에 노트를 더하면 배치 8개의 엔진 클립 모두가 함께 바뀐다. `change`가 그 패턴을 변경으로 보고한다.
2. 베이스 생성. 채널·인서트·패턴·레인·배치 8개를 한 요청으로 만들고 모두 실제로 연주된다. `change`가 추가된 ID를 보고한다.
3. 구간 재배치. 뒤 네 마디 드럼을 옮기고 `change`가 변경된 클립 4개를 보고한다.
4. 믹스 조정. 베이스 인서트의 게인을 내리고 limiter를 걸면 엔진 트랙에 실제 플러그인이 붙는다.

그런 다음 Undo 네 번으로 네 작업이 역순으로 하나씩 되돌아간다. 요청 하나가 Undo 하나다.

마지막으로 앱에서 채널을 추가해 revision을 올린 뒤 오래된 스냅샷을 제출하면 거절되고 프로젝트는 그대로다. `apply_change`로 다시 읽어 같은 편집을 얹으면 성공한다. 그 사이 session ID는 그대로이고 재생도 멈추지 않는다.

MIDI learn과 하드웨어 컨트롤 서피스 연결은 없다. 여러 외부 도구가 동시에 쓰는 경우의 요청 큐는 여전히 없다. 마지막에 쓴 쪽이 이기고 나머지는 revision 충돌로 거절된 뒤 다시 읽는다. 실제 청음과 타사 VST3 호환성은 여전히 미검증이다.

## 2026-09-10 — M8 화면 기능 동등성 점검과 배포 안정화

`docs/claude-handoff-milestones.ko.md`의 M8을 수행했다.

### 메뉴 전수 점검

모든 메뉴 명령을 실제 프로젝트에 대해 순서대로 실행하는 검사를 넣었다. 명령마다 필요한 선택 상태를 갖춘 뒤 실행하고, 하나라도 실행되지 않으면 검사가 실패한다. 동작하지 않는 버튼이 화면에 남아 있으면 여기서 드러난다.

이 점검이 실제로 한 가지를 잡아냈다. 노트가 없는 패턴이 선택된 상태에서는 반음 이동이 비활성인데, 이는 의도한 동작이므로 검사 쪽 순서를 고쳤다.

`Open project folder`만 제외했다. 탐색기 창을 여는 명령이라 검사에서 반복 실행할 것이 아니다.

### 자동화 우선권 버그

M6에서 넘어온 실제 버그를 고쳤다. 렌더가 모델의 채널 볼륨을 매번 엔진에 써 넣는데, 그 파라미터에 자동화 곡선이 걸리면 자동화가 값을 움직이는 족족 모델 값으로 되돌려 곡선이 들리지 않았다. 이제 곡선이 있는 파라미터에는 모델 값을 쓰지 않는다. 곡선이 사라지면 엔진 곡선도 지우고 파라미터는 다시 모델 값을 따른다.

M6 검사도 이에 맞춰 고쳤다. 4OSC의 필터는 기본값이 꺼짐이라 `filterFreq` 자동화는 들리지 않는다. 채널 볼륨에 곡선을 걸어 렌더 RMS가 실제로 내려가는지, 곡선을 지우면 다시 올라오는지, 그동안 모델의 `gain_db`는 그대로인지를 확인한다.

### 배율·누락 플러그인·비정상 종료

`--scale` 진단 옵션을 더해 150%와 200%에서 화면이 배치되는지 확인한다. 스냅샷 크기가 커지고 상태줄 라벨이 그대로 나오는지를 본다.

설치되지 않은 플러그인 식별자를 악기로 지정해도 채널과 트랙은 남고 오류도 나지 않는다. 나중에 스캔하면 그때 붙는다.

20초 동안 재생을 유지하며 오류가 없는지 확인한 뒤 프로세스를 강제 종료하고 다시 연다. 마지막으로 발행된 상태의 채널·패턴·배치·엔진 클립이 그대로 돌아온다.

### 도구 다듬기

이 과정에서 실제 문제 세 가지를 고쳤다.

`ui.png`를 임시 파일로 쓴 뒤 교체하도록 바꿨다. 외부 도구가 쓰는 중인 파일을 읽어 잘린 이미지를 보는 일이 없다.

`control.json` 요청도 revision 충돌 시 다시 읽고 보내도록 했다. 전송 도중 앱이 상태를 갱신하면 종료 명령조차 거절될 수 있었다.

`--ui-script`는 파일 내용이 바뀔 때 다시 읽는데, 같은 동작을 연속으로 보내면 내용이 같아 무시됐다. 무시되는 `comment` 표시를 넣어 회차를 구분한다.

### 검증

`tools/test_live_sync.py`가 23개로 늘었고 전부 통과했다. 배포 ZIP에서 꺼낸 실행 파일로도 23개 전부 통과했고, `tools/test_portable_start.ps1`로 개발 도구 없는 PATH에서 더블클릭 실행과 기존 프로젝트 복원도 확인했다.

23개 검사가 기능 표의 각 행을 지난다. 상단 메뉴와 transport는 전수 점검, Browser는 자산·검색·미리듣기·누락 찾기, Channel Rack은 스텝·악기·볼륨·팬·인서트, Pattern picker는 생성·복제·배치 수, Playlist는 배치·이동·분할·복제·루프, Mixer는 라우팅·센드·여섯 효과·미터, 자동화·녹음·렌더가 각각 검사에 들어 있다.

### 남은 제한

설치 프로그램·코드 서명·자동 업데이트는 배포 채널을 정한 뒤 별도 작업이다. 마일스톤 문서도 그렇게 적고 있다.

실제 오디오 청취와 타사 VST3 호환성은 이 환경에 오디오 장치와 플러그인이 없어 끝까지 검증하지 못했다. 렌더한 WAV의 길이·무음 여부·클리핑은 검사하지만 사람이 들어본 것은 아니다.

실제 입력 장치를 연결한 녹음은 이 환경에 장치가 없어 검사하지 못했다. 대신 녹음이 트랙에 남기는 것과 같은 모양의 클립을 만들어 두고, 그것을 모델이 패턴과 배치로 가져가는 경로를 검사에 넣었다. 장치에서 들어오는 신호 자체는 여전히 미검증이다. 100% 기준의 실제 고DPI 디스플레이와 오디오 장치 교체도 장치가 필요해 검사하지 못했다. autosave/history/preset 정리는 세션 저장과 Undo 기록 초기화 수준까지만 되어 있고 별도의 백업 회전은 없다.

## 2026-09-10 — N1 출력 데이터 보존 및 렌더 경계

`docs/review-next-milestones-2026-09-10.ko.md`의 N1과 R4를 수행했다. 먼저 재현 검사를 만들고 실패를 확인한 뒤 고쳤다.

### R1 동명 채널 스템 덮어쓰기

재현됨. 이름이 둘 다 `Lead`인 채널을 스템으로 내보내면 `stems/Lead.wav` 하나만 남고 결과 목록에는 같은 경로가 두 번 들어갔다.

렌더를 시작하기 전에 모든 목적지를 먼저 정하도록 바꿨다. 이름을 파일명으로 정규화한 뒤 이미 쓴 이름이면 번호를 붙인다. 대소문자 차이도 같은 이름으로 본다. 파일 하나라도 실패하면 메시지에 실패 개수를 함께 보고한다.

### R2 실패 전 기존 WAV 삭제

렌더 결과를 목적지 옆의 고유한 임시 파일에 쓰고, 렌더가 성공했고 파일이 비어 있지 않은 것을 확인한 뒤에야 목적지로 옮긴다. 실패하면 임시 파일을 지우고 이전 결과는 그대로 둔다. 목적지가 디렉터리인 경우도 실패로 처리한다.

### R3 스템에서 빠지던 send

스템이 채널 트랙과 인서트의 output 사슬만 따라가서, send로만 들리는 리버브 버스가 빠져 있었다. 이제 출력 사슬과 send 대상, 그리고 그 대상의 출력 사슬까지 너비 우선으로 모은다.

wet 버스는 여러 채널이 공유하므로 개별 스템의 합이 전체 믹스와 같다고 보장하지 않는다. 문서에 그 의미를 적었다.

### 렌더 경계

리뷰의 조사 항목이었다. Exporter가 살아 있는 Edit를 백그라운드에서 읽는 동안 메시지 스레드는 계속 편집을 적용했다.

렌더 시작 시점에 `edit.state`의 사본을 뜨고, 작업 스레드에서 그 사본을 `EditRole::forRendering`으로 연 별도 Edit를 렌더한다. 스템 선택도 시작 시점에 트랙 인덱스로 확정한다. 열려 있는 프로젝트는 렌더가 도는 동안에도 그대로 편집되고, 그 편집은 다음 렌더부터 반영된다. 프로젝트를 다시 여는 방식으로 우회하지 않았다.

`render-status.json`에 `revision`과 `complete`를 더했다. 어느 시점의 프로젝트를 렌더했는지, 요청한 파일을 모두 썼는지 외부에서 확인할 수 있다.

### R4 CI gate

workflow가 빌드 후 ZIP을 풀어 통합 검사와 배포본 시작 검사를 실행하고, 둘 다 통과해야 artifact를 올린다. 검사 보고서와 스크린샷은 실패해도 별도 artifact로 남긴다.

`tools/test_portable_start.ps1`이 기존 프로젝트가 없는 기계에서도 동작하도록 고쳤다. 먼저 한 번 띄워 기본 프로젝트를 만들고, 두 번째 실행에서 복원되는지 확인한다.

CI 러너에는 오디오 장치와 타사 플러그인이 없다. 그 제약으로 실행할 수 없는 검사는 CI에서 수행하지 않으며 실장치 검증으로 간주하지 않는다.

### 검증

`tools/test_live_sync.py`가 24개로 늘었고 전부 통과했다. 새 검사는 이번 수정의 재현 검사다.

1. 이름이 같은 채널 둘이 서로 다른 파일로 나오고 둘 다 소리가 있다.
2. send를 없애면 스템 파일이 달라진다. 즉 스템이 send를 담고 있다.
3. 목적지를 쓸 수 없게 만든 뒤 렌더하면 실패로 보고되고 이전 믹스의 해시가 그대로다.
4. 렌더가 도는 동안 외부에서 반복 편집·Undo를 넣어도 렌더는 시작 시점 revision을 보고하며 완료되고, 결과 WAV는 무음이 아니며, 프로젝트는 같은 세션으로 멀쩡하다.

이번 실행은 로컬 빌드 기준이다. 배포 ZIP 검사와 CI gate 동작은 다음 push에서 확인한다.

### 남은 제한

렌더 사본은 `EditRole::forRendering`으로 열리므로 실제 재생 장치를 쓰지 않는다. 타사 VST3가 렌더 전용 Edit에서 상태를 그대로 복원하는지는 플러그인이 없어 확인하지 못했다. 스템의 dry/wet 의미는 문서로 정의했을 뿐 사람이 들어 확인한 것은 아니다.

## 2026-09-10 — N2 녹음과 프로젝트 복구

`docs/review-next-milestones-2026-09-10.ko.md`의 N2를 수행했다.

### 종료 경로 통합

리뷰가 지적한 대로 종료 경로가 둘이었다. 메뉴는 `Recorder::stopRecording`을 지나 take를 가져갔지만 외부 `control.json`의 `stop`은 `transport.stop`만 불러 take가 버려지고 클릭 설정도 되돌아오지 않았다.

이제 모든 종료가 한 곳을 지난다. 화면의 Play/Stop, `Ctrl+Shift+R`, 외부 `stop`, 창을 닫는 것 모두 같다. 외부에서 `record`로 녹음을 시작·중지할 수 있게 했고 `sync-status.json`에 `recording`을 더해 상태를 밖에서 볼 수 있게 했다.

take를 보관한 직후에는 세션을 저장하고 백업까지 바로 만든다. 녹음은 다시 만들 수 없으므로 다음 자동 저장까지 기다리지 않는다.

### 백업 회전과 복구

작업 폴더의 `backups`에 세션 사본을 쌓는다. 내용이 바뀌는 동안 1분에 한 번, take 보관 직후와 종료 시에는 즉시 쓰며 최신 10개만 남긴다.

세션 파일이 없거나 열리지 않으면 시작할 때 가장 최근의 열리는 백업으로 복구한다. 백업이 있는 폴더는 이전에 세션이 있었다는 뜻이므로 새 프로젝트로 시작하지 않는다. 어느 파일에서 복구했는지 `recovered_from`에 남기고 상태줄에도 표시한다.

`File > Restore a backup...`은 목록에서 고른 백업을 다음에 열릴 세션으로 만들고 현재 세션을 함께 보관한다. 열려 있는 Edit를 도중에 교체하지 않는다.

### 누락 자산 안내

클립이 찾지 못하는 샘플 이름을 `sync-status.json`의 `missing_assets`에 싣고, 시작할 때 상태줄에 Browser의 Find를 쓰라고 안내한다.

### 검증

`tools/test_live_sync.py`가 25개로 늘었다. 새 검사는 한 세션에서 다음을 확인한다.

1. 외부 `record`로 녹음을 시작하고 외부 `stop`으로 멈춰도 take가 패턴과 배치로 남는다. 노트와 시작 위치가 일치하고 전송은 멈춰 있다.
2. 편집이 이어지는 동안 백업이 최신순으로 쌓이고 개수 상한을 넘지 않는다.
3. 앱을 강제 종료하고 세션 파일을 지운 뒤 다시 열면 백업에서 복구되고, 방금 만든 take까지 남아 있다.
4. 샘플 파일을 지우면 `missing_assets`에 이름이 나타난다.

R4로 넣은 CI gate가 실제 러너에서 통과하는 것도 확인했다. 빌드 후 ZIP을 풀어 통합 검사와 배포본 시작 검사를 지나야 artifact가 올라간다.

### 남은 제한

실제 MIDI 키보드와 오디오 인터페이스로 하는 녹음은 이 환경에 장치가 없어 여전히 미검증이다. 검사는 녹음이 트랙에 남기는 것과 같은 모양의 클립을 만들어 종료 경로와 모델 편입을 확인한다. 입력 장치 선택 UI는 없고 사용 가능한 입력을 모두 arm한 채널에 연결한다. 오디오 take의 원본 오프셋과 믹서 경로 보존은 실녹음으로 확인해야 한다.

## 2026-09-10 — N3 화면으로 끝내는 작곡 흐름

`docs/review-next-milestones-2026-09-10.ko.md`의 N3을 수행했다.

### 자동화 곡선 편집기

M6에서 남았던 항목이다. 곡선은 곡 전체의 시간축을 쓰므로 패턴 안의 피아노롤이 아니라 편곡 격자 아래에 줄로 붙였다. 줄마다 파라미터 이름과 소유한 채널·인서트를 적고, 엔진이 따라갈 선과 점을 그린다.

빈 곳을 누르면 점이 생기고, 끌면 시간과 값이 함께 움직이고, 오른쪽 버튼이나 `Delete`로 지운다. 스냅과 확대는 편곡과 같은 설정을 쓴다. 모든 편집은 모델의 점을 고치므로 외부 편집과 같은 경로이고 Undo도 같다.

Playlist 툴바의 `Automate`가 선택한 채널의 악기·페이더와 그 채널이 지나는 인서트 효과의 파라미터를 모아 보여준다. 고르면 곡선이 생기고, 같은 메뉴에서 곡선을 없앨 수도 있다.

### 프리셋과 이력

채널 행의 `P` 버튼이 악기 설정을 이름 붙여 저장하고 다시 불러온다. 파일은 플러그인 자신의 상태이므로 같은 종류의 악기에만 적용한다. Tools 메뉴에도 같은 명령을 넣어 키보드로도 닿게 했다.

Undo/Redo 메뉴가 무엇을 되돌리는지 함께 표시한다.

### CI에서 드러난 렌더 버그

N1에서 넣은 렌더 스냅샷이 CI에서 멈췄다. 렌더용 Edit를 작업 스레드에서 만든 것이 원인이었다. Edit는 메시지 스레드에서 만들고 없애야 한다. 이제 렌더 시작 시 메시지 스레드에서 사본 Edit를 열고, 작업 스레드는 그 위에서 렌더만 돌리며, 결과를 걷을 때 메시지 스레드에서 Edit를 놓는다.

로컬에서는 통과하고 러너에서만 걸린 문제였다. gate가 없었으면 이 빌드가 그대로 배포됐을 것이다.

### 검증

`tools/test_live_sync.py`가 26개로 늘었다. 새 검사는 N3의 완료 조건이다. JSON을 손으로 쓰지 않고 화면이 제공하는 것만으로 다음을 수행한다.

1. 스텝 그리드로 드럼과 베이스를, 피아노롤로 멜로디를 써서 한 패턴에 세 채널을 넣는다.
2. 편곡에 여덟 번 배치하고 샘플을 레인에 놓는다.
3. `Automate`로 채널 볼륨 곡선을 열고 점을 찍고 끌고 지운다. 남은 점의 시간과 값이 맞고 엔진에도 같은 수가 들어간다.
4. Undo 한 번이 마지막 점 편집을 되돌리고 Redo가 되돌린다.
5. 악기 프리셋을 저장한다.
6. 재생하고 믹스를 렌더해 무음도 클리핑도 아닌 파일을 얻는다.
7. 그 상태에서 외부 편집이 같은 열린 세션에 반영된다.

화면은 스크린샷으로도 확인했다. 편곡 아래에 두 개의 곡선 줄이 그려지고 믹서 미터가 볼륨 곡선을 따라 움직인다.

### 남은 제한

MIDI learn은 구현하지 않았다. 장치가 없어 확인할 수 없는 기능을 화면에 넣지 않기로 했고, N4에서 실제 장치가 붙을 때 함께 다룬다. 곡선의 모양(curve) 값은 모델과 외부 편집에서만 바꾸며 화면에는 직선으로 그린다. 프리셋은 같은 종류의 악기끼리만 오간다. 실제 청음과 타사 VST3 호환성은 여전히 미검증이다.

## 2026-09-10 — N4 실제 환경 호환성과 장시간 안정성

`docs/review-next-milestones-2026-09-10.ko.md`의 N4를 수행했다. 결과는 `docs/compatibility-2026-09-10.ko.md`에 표로 있다.

### 검사 도구 두 개

`tools/test_plugin_compatibility.py`는 이 기계에 실제로 설치된 VST3를 상대로 스캔·로드·창·자동화·렌더·재시작 복원을 확인한다. `tools/test_real_environment.py`는 플러그인이 아니라 기계를 본다. 어떤 오디오 장치가 열렸는지, 재생과 정지가 실제로 도는지, 100/150/200% 배율에서 창이 어떻게 열리는지, 반복 저장과 Undo 뒤에도 프로젝트가 제자리인지, 한 시간 넘게 재생해도 버티는지다.

### 표

VST3 23개(악기 12, 효과 11)가 모두 올라오고 파라미터를 보고하고 자기 창을 띄우고 자동화를 받고 재시작 뒤 돌아온다. 악기 여럿은 렌더 peak가 0인데, 자기 라이브러리를 따로 불러와야 소리가 나는 종류다. 앱의 실패가 아니라 플러그인 창에서 사람이 음색을 고르는 단계가 남은 것이다.

### 이 과정에서 나온 버그 네 개

나머지 셋은 200% 배율에서 창이 화면보다 커지던 문제, 믹서가 내장 효과 6개만 제공하던 문제, 두 번째 프로젝트를 열면 아무 일도 일어나지 않던 문제다. 넷 다 고쳤고 재현 절차와 함께 호환성 문서에 적었다.

## 2026-09-10 - N5 검증된 Windows 릴리스

`docs/review-next-milestones-2026-09-10.ko.md`의 N5를 수행했다. 배포 방식·서명·업데이트 채널 결정은 `docs/release.ko.md`에 있다.

### 배포물이 자기 이력을 들고 다닌다

`tools/build-windows.ps1`이 패키징 직전에 `BUILD-INFO.json`을 만든다. 버전, 만들어진 커밋, 그 커밋의 작업 트리가 깨끗했는지, 빌드 시각, 실행 파일의 SHA-256과 크기가 들어간다. 이 파일은 ZIP 안에 들어가므로 손에 든 빌드가 무엇인지 파일 하나로 알 수 있다.

검사가 모두 끝난 뒤 `tools/finish_release.ps1`이 검사 보고서와 문서를 ZIP의 `verification/`에 넣고 그때의 ZIP 해시를 `SHA256SUMS.txt`에 쓴다. 순서가 중요하다. 해시는 보고서까지 들어간 뒤, 즉 사람이 실제로 내려받는 파일에 대해 계산된다. 보고서가 없으면 이 스크립트는 거절한다. 검사를 건너뛴 배포물이 봉인될 수 없다는 뜻이다.

### 설치·업데이트·제거

이식형 ZIP이 배포물이고 압축만 풀면 실행된다. 원하는 사람을 위해 `Install.cmd`를 넣었다. `%LOCALAPPDATA%\Programs\CoCompose`로 복사하고 시작 메뉴에 바로가기를 만든다. 관리자 권한을 쓰지 않고, PowerShell을 전체 경로로 부르므로 PATH가 이상한 기계에서도 바로가기가 생긴다. 같은 폴더에 남는 `Uninstall.cmd`는 프로그램과 바로가기만 지운다.

프로젝트는 설치 폴더 밖(`Documents\CoCompose`)에 있다. 그래서 새 빌드로 `Install.cmd`를 다시 실행하는 것이 곧 업데이트이고 작업물은 그대로다.

설치 EXE는 만들지 않기로 했다. 하는 일이 폴더 복사와 바로가기 생성뿐이라 EXE가 더 해주는 것이 없고, 서명 없는 설치 EXE는 SmartScreen이 더 강하게 막는다. 코드 서명은 하지 않고 대신 해시를 낸다. 자동 업데이트도 넣지 않는다. 앱이 네트워크에 나가지 않는데 서명 없는 바이너리를 스스로 받아 실행하는 경로를 만들 이유가 없다. 셋 다 대가를 문서에 적었다.

### 새 검사

`tools/test_install_and_update.ps1`이 설치 → 프로젝트 작성 → 같은 설치 반복 → 프로젝트가 그대로인지 → 제거 → 프로젝트가 여전히 남아 있는지를 확인한다. 개발 도구가 하나도 닿지 않는 PATH에서 돌린다.

이 검사를 쓰면서 스크립트 쪽 실수를 두 개 잡았다. PowerShell 5.1의 `Start-Process -ArgumentList` 배열은 공백이 든 경로에 따옴표를 붙이지 않아 앱에 인자가 쪼개져 도착한다. 그리고 자기가 들어 있는 폴더를 지우는 배치 스크립트는 `cmd /c` 중첩 따옴표로는 제대로 동작하지 않아, 분리된 PowerShell에게 넘기도록 고쳤다.

### CI 순서

빌드 → 패키징 → ZIP 압축 해제 → 압축을 푼 실행 파일로 통합 검사 26개 → 두 번 누른 것처럼 시작 → 설치·업데이트·제거 → 봉인 → 업로드. 앞이 하나라도 실패하면 뒤가 실행되지 않고 배포물은 올라가지 않는다. ZIP과 함께 `SHA256SUMS.txt`도 올린다.

전체 순서를 이 기계에서 한 번 그대로 돌려 확인했다. 통합 검사 26개 통과, 이식형 시작 복원 통과, 설치·업데이트·제거 통과, 봉인 후 해시 재계산 일치.

### gate가 또 두 개를 잡았다

CI에 올리자 두 번 막혔다. 둘 다 실제 문제였다.

하나는 진짜 버그다. 오디오 장치가 없는 러너에서는 검사가 transport 대신 스크립트로 take를 모델에 접어 넣는데, 그 경로가 저장과 백업을 하지 않았다. transport로 멈추는 경로만 하고 있었다. take가 메모리에만 남아 세션을 잃으면 함께 사라진다. 이제 take를 지키는 모든 경로가 한 곳을 지난다. 검사도 고쳤다. 장치가 있는 기계에서는 그 경로를 아예 실행하지 않았기 때문에 로컬에서 보이지 않았던 것이라, 이제 장치가 있어도 두 번째 take는 그 경로로 지킨다.

다른 하나는 검사 쪽 실수다. 200% 배율에서 창 크기가 620x340 이상이어야 한다고 적어뒀는데, 그 숫자는 이 기계의 2560x1440 화면에서 나온 값이다. 1024x768 러너에서는 창이 504x324로 줄어드는 것이 올바른 동작인데 검사가 실패했다. 화면에 의존하지 않는 성질로 바꿨다. 창이 화면에 들어가고, 찌그러지지 않았고, 100%에서 배치하는 라벨을 전부 배치한다.

### 실제로 확인한 것

CI가 통과한 뒤 올라온 artifact를 다시 내려받아 확인했다. `SHA256SUMS.txt`의 값과 내려받은 ZIP의 해시가 일치한다. 안에는 `BUILD-INFO.json`(커밋 7564148, 작업 트리 clean), 변경 기록, `Install.cmd`, `Uninstall.cmd`, 라이선스, 그리고 `verification/`에 검사 보고서와 문서가 들어 있다. 이 ZIP을 풀어 `Install.cmd`로 설치하고, 다시 설치해 업데이트하고, 제거하는 것까지 이 기계에서 돌렸다. 프로젝트는 세 단계 모두에서 그대로였다.

### 남은 제약

## 2026-09-10 - P0 데이터 보존과 배포 검증 보강

`docs/review-next-milestones-v2-2026-09-10.ko.md`의 P0. V2-R1/R2/R3 세 건을 재현하고 고쳤다.

### V2-R1 최종 WAV 교체가 기존 파일을 먼저 지웠다

`moveFileTo`는 대상 파일을 지우고 나서 옮긴다(`juce_File.cpp:300`). 그 사이에 무슨 일이 생기면 마지막으로 성공했던 렌더가 사라진다. `replaceFileIn`은 Windows `ReplaceFile`을 쓰므로 실패해도 기존 파일을 그대로 둔다. 그쪽으로 바꿨다.

재현은 파일을 잠그는 방식으로는 되지 않았다. 요즘 Windows는 delete가 이름을 즉시 비우므로 지운 직후의 이동이 성공한다. 창이 좁을 뿐 없어진 것이 아니라서, 창이 있었는지 자체를 물어보기로 했다. `ReadDirectoryChangesW`로 폴더를 지켜보며 다시 export하면, 고치기 전에는 `mix.wav`의 removed 이벤트가 남고 고친 뒤에는 남지 않는다. 검사가 옛 동작을 실제로 잡는지 확인하려고 한 줄만 되돌린 빌드로도 돌려봤다. 이벤트가 나왔다.

교체 실패 자체도 검사한다. 대상 파일을 아무것도 공유하지 않는 핸들로 열어두면 교체가 반드시 실패한다. 이때 기존 WAV는 해시까지 그대로여야 하고, 이미 끝난 렌더는 버리지 않고 `mix-rendering-<id>.wav`로 남겨 이름을 알려줘야 한다. 렌더 실패와 교체 실패는 다른 일이다. 전자는 남길 것이 없고 후자는 시간을 들여 만든 온전한 파일이 있다. 메시지도 둘을 구분한다.

### V2-R2 봉인 스크립트가 아무 보고서나 받았다

`finish_release.ps1`은 보고서 파일이 있는지만 봤다. 리뷰어가 dummy ZIP과 `{"passed":false}` 보고서로 통과시키는 것을 재현해뒀다. 지금은 그 재현이 거절된다.

검사 보고서에 `schema`, `result`, `checks`, 검사한 실행 파일의 SHA-256, 커밋, 끝난 시각을 적는다. 통합 검사가 실패해도 보고서를 남긴다. 실패했다고 적힌 보고서가 있어야 배포 단계가 그것을 거절할 수 있고, 그렇지 않으면 실패의 증거가 콘솔 로그뿐이다.

봉인은 이제 보고서를 읽는다. JSON인지, 아는 형식인지, 통과라고 적혀 있는지, 검사 수가 최소치 이상인지, 그리고 **보고서가 검사한 실행 파일이 이 ZIP 안의 실행 파일과 같은지**를 본다. 마지막 항목이 핵심이다. 이것이 없으면 아무 빌드의 보고서로 아무 배포물이나 봉인된다. 넣으라고 지정한 문서가 없으면 조용히 넘어가지 않고 거절한다.

`tools/test_release_seal.ps1`이 이것을 검사한다. 실패한 보고서, 검사 0개, 다른 빌드의 보고서, 모르는 형식, 실행 파일을 밝히지 않는 보고서, JSON이 아닌 파일, 없는 보고서, 없는 첨부 문서. 여덟 가지 모두 거절되고 거절하면서 배포물을 건드리지 않는지도 확인한다. 올바른 보고서 하나는 통과한다. 전부 임시 fixture로 하며 실제 배포물은 손대지 않는다.

### V2-R3 제거 실패를 성공으로 보고했다

제거를 2초 뒤 별도 프로세스에 맡기고 부모는 곧바로 성공을 출력했다. 앱이 실행 중이면 실행 파일이 잠겨 아무것도 지워지지 않는데도 성공으로 보였고, 바로가기는 이미 지워져 반쯤 제거된 상태가 됐다.

고치는 동안 왜 이런 모양이었는지가 분명해졌다. cmd는 배치 파일을 실행하면서 디스크에서 계속 읽는다. 자기 폴더가 지워지기를 기다리는 스크립트는 도중에 읽을 수 없게 된다. 그래서 확인할 수 있는 일은 전부 그 자리에서 한다. 실행 중인지 보고, 바로가기를 지우고, 자기 자신을 뺀 모든 설치 파일을 지운 뒤 무엇이 남았는지 되묻는다. 남으면 무엇이 어디에 남았는지 알리고 4로 끝난다. 실행 중이면 아무것도 지우지 않고 3으로 끝난다. 마지막에 남는 것은 이 스크립트와 빈 폴더뿐이고 그것만 분리된 프로세스가 치운다.

찾는 김에 두 가지가 더 나왔다. `find`와 `timeout`을 이름으로 불러 PATH에 다른 도구가 있는 기계에서 엉뚱한 것이 실행됐다. `timeout`은 stdin이 리디렉션되면 아예 거부한다. 이제 Windows가 주는 것을 전체 경로로 부른다. `start`는 스위치를 제목보다 먼저 읽으므로 `start "" /min`의 `/min`은 실행할 프로그램으로 취급됐다. `start /min ""`로 고쳤다.

`tools/test_install_and_update.ps1`이 실행 중 제거가 3으로 거절되고 그때 실행 파일과 바로가기가 그대로 남는지도 확인한다.

## 2026-09-10 - P1 렌더·종료·플러그인 상태 경계

`docs/review-next-milestones-v2-2026-09-10.ko.md`의 P1. 리뷰의 "추가 조사 항목" 네 가지를 확인하고 그 과정에서 나온 것을 고쳤다.

### 렌더 도중 종료

엔진은 렌더를 도는 스레드가 종료 신호를 받으면 렌더를 멈춘다(`Renderer::RenderTask::getDefaultCancellationCheck`가 `juce::Thread::currentThreadShouldExit()`을 본다). 그래서 30초 안에 안 멈추고 강제 종료되는 상황은 실제로는 일어나지 않았다. 다만 `renderToFile`은 출력 파일이 존재하는지를 결과로 돌려준다. 중간까지 쓰인 파일도 존재하므로, 그 답을 믿으면 잘려 나간 파일이 마지막으로 성공한 렌더 자리에 들어갈 수 있다. 이제 그 답과 무관하게 중단된 렌더는 실패로 다룬다.

검사도 붙였다. 렌더는 실시간보다 70배쯤 빨라서 sleep으로는 도중을 맞출 수 없다. 그래서 export 다음 동작으로 Exit를 같은 스크립트에 넣었다. 한 틱 뒤에 종료가 들어가므로 확실히 렌더 도중이다. 종료 후 확인하는 것은 세 가지다. 렌더가 완료로 보고되지 않았을 것, 이전에 완성된 WAV가 해시까지 그대로일 것, 반쯤 쓰인 `mix-rendering-*` 파일이 남아 있지 않을 것. 그리고 다시 열었을 때 채널 16개와 패턴 길이가 그대로일 것.

한 가지는 분명히 해둔다. 이 검사는 위 수정을 지웠을 때도 통과한다. 지금 엔진이 취소된 렌더에서 부분 파일을 남기지 않기 때문이다. 수정은 엔진의 반환값에 기대지 않겠다는 것이지 이 검사가 잡아내는 회귀는 아니다.

### 렌더가 끝났지만 아직 걷지 않은 사이

`isBusy()`가 스레드가 도는지만 봤다. 스레드가 끝나고 앱이 결과를 걷기 전 사이에 새 export가 시작되면, 아직 읽지 않은 결과가 있는 채로 렌더용 Edit가 교체된다. 이제 결과를 걷을 때까지 busy다.

이 창을 밖에서 노려 맞히는 검사는 만들 수 없어서, 대신 확실히 겹치는 경우를 검사한다. 한 스크립트에서 export를 연달아 두 번 요청하면 두 번째는 거절되고, 첫 번째 렌더는 방해받지 않고 끝까지 나온다. 거절되는 것이 결과가 요청에 붙어 있게 하는 방법이다.

### 플러그인이 들고 있는 상태

플러그인은 자기 설정을 자기 안에 들고 있고 가끔씩만 프로젝트에 적어 넣는다. 렌더는 프로젝트의 사본으로 도니까, 사본을 뜨기 전에 `edit.flushState()`를 부르지 않으면 방금 플러그인 창에서 바꾼 음색이 사본에 없다. 이제 사본을 뜨기 전에 부른다.

공개 파라미터를 JSON으로 바꾼 직후의 렌더가 그 변경을 따라가는 것은 확인했다. 플러그인 창 안에서 사람이 노브를 돌린 경우는 사람이 해야 확인되므로 P2로 넘긴다.

### 이 과정에서 나온 버그: 루프가 선택을 따라오지 않았다

렌더는 루프 구간을 대상으로 한다. 그런데 루프를 정하는 `applyTransportMode()`는 앱 시작할 때와 Song mode 명령을 누를 때만 불렸다. 그래서 패턴을 길게 늘이거나 다른 패턴을 고른 뒤 export하면 예전 루프 구간이 렌더됐다. 패턴을 200박으로 늘리고 export했더니 32박만 나왔다.

이제 선택·리비전·모드가 달라졌을 때만 다시 계산해서 루프에 반영한다. 값이 실제로 달라졌을 때만 쓰므로 재생 중에 재생 위치가 튀지 않는다.

### 설치 스크립트의 작은따옴표

리뷰가 짚은 대로 `Install.cmd`와 `Uninstall.cmd`가 경로를 PowerShell 작은따옴표 문자열 안에 그대로 넣고 있었다. 사용자 이름에 작은따옴표가 있으면 문자열이 거기서 끝난다. cmd의 치환으로 따옴표를 두 번씩 만들어 넣도록 고쳤다.

### 검증

통합 검사가 27개로 늘었다. 새 검사는 위의 종료·중복 export·리비전 연결을 다룬다.

이번에 다시 실행하지 않은 것: VST 호환성 표, 65분 재생, 실제 청음, CI 원격 실행. 실제 플러그인 창에서 음색을 바꾼 뒤의 렌더도 미검증이다.

## 2026-09-11 - P3 남은 편집 기능 완결

`docs/review-next-milestones-v2-2026-09-10.ko.md`의 P3. 화면만으로 못 하던 세 가지를 채웠다.

### 곡선 모양

이전에는 점을 직선으로 이었다. 엔진은 점마다 curve 값(-1~1)을 갖고 그 값으로 구간을 휘게 만드는데, 그 값은 외부 JSON으로만 바꿀 수 있었고 화면은 직선만 그렸다.

그리는 쪽부터 고쳤다. 화면의 선을 다시 계산하지 않고 엔진에게 물어본다. 픽셀마다 `AutomationCurve::getValueAt`을 읽어 그린다. 그러면 화면과 엔진이 어긋날 방법이 없다. 플러그인이 없어 물어볼 대상이 없을 때만 점을 직선으로 잇는다.

편집은 Ctrl 또는 Alt를 누른 채 두 점 사이의 선을 끄는 것이다. 위로 끌면 한쪽으로, 아래로 끌면 반대로 휜다. 모양은 그 구간을 시작하는 점에 저장되며, 엔진이 같은 자리에 두는 것과 같다. Undo 한 번이 되돌린다.

`state.json`의 각 곡선에 `engine_samples`가 생겼다. 엔진에게 곡선의 처음부터 끝까지 아홉 번 물어본 값이다. 모양이 없으면 직선으로 읽히고 휘면 휘어서 읽힌다. 모델이 아니라 엔진이 답한 값이므로, 모양이 실제로 전달됐는지를 이것으로 확인한다.

### MIDI learn

엔진에는 컨트롤러 매핑 기능이 이미 다 있었다. 매핑은 Edit 안에 저장되고 프로젝트와 함께 복원된다. 그런데 들어온 컨트롤 메시지는 "지금 포커스를 가진 Edit"에게만 전달되고, 그 질문의 기본 답이 "없음"이었다. CoCompose는 그 답을 준 적이 없다. 그래서 MIDI learn은 미구현이 아니라 아예 닿을 수 없는 상태였다.

한 번에 한 프로젝트만 여는 앱이므로 답은 언제나 그 프로젝트다. 그것만 알려주자 엔진의 기능이 그대로 살아났다.

learn 자체는 이렇게 한다. 엔진의 행(row)은 파라미터를 자기 메뉴로만 받으므로, 매핑을 Edit에 먼저 써 넣고(자리표시자 컨트롤러 1번) 그 행을 listen 상태로 만든다. 컨트롤러가 오면 자리표시자를 덮어쓰고 저장한다. 아무것도 오지 않은 채 취소하면 매핑을 지운다. 팔린 채로 잘못된 매핑이 남지 않게 하기 위해서다.

Playlist의 `Automate` 메뉴에 `MIDI learn`이 생겼다. `state.json`의 `automation.midi_mappings`가 무엇이 무엇에 걸렸는지 보여준다.

검사는 컨트롤러를 흉내 내되 진짜와 같은 지점으로 넣는다(`ParameterControlMappings::sendChange`). CC74를 학습시키고, 그 CC가 파라미터를 움직이는지, 앱을 닫았다 열어도 매핑이 남아 여전히 움직이는지 확인한다.

### 프리셋

프리셋이 안 맞으면 조용히 아무 일도 일어나지 않았다. 이제 왜 안 되는지 말한다. "Drums 4OSC is for 4OSC, and this channel is playing Sampler" 같은 식이다. 메뉴에서도 맞지 않는 프리셋을 감추지 않고 무엇을 위한 것인지 적어 흐리게 보여준다.

이러면서 상태 표시줄의 동작을 고쳤다. 지금까지는 "이 접두어로 시작하는 문장은 덮어쓰지 않는다"는 목록으로 유지했다. 새 문장은 그 목록에 없으니 다음 틱에 지워졌다. 목록을 없애고 마지막 문장이 8초 지나면 기본 안내로 돌아가게 했다. 그리고 앱이 사람에게 한 말을 `sync-status.json`의 `message`에 함께 적는다. 외부 도구가 무슨 일이 있었는지 읽을 수 있고, 검사도 라벨을 뒤지는 대신 그것을 본다.

### 이 과정에서 나온 버그: 건반을 꽂으면 프로젝트가 바뀐 것으로 취급됐다

P2에서 `state.json`에 입력 장치 목록을 넣었는데, MIDI 입력은 앱이 뜨고 1초쯤 뒤에 나타난다. revision은 스냅샷 전체를 비교해 정하므로 입력이 나타나는 순간 revision이 올라갔다. 밖에서 읽어둔 상태로 편집을 보내던 도구는 그 순간 충돌을 맞는다.

장치와 입력 목록은 기계에 관한 사실이지 곡에 관한 사실이 아니다. 그래서 공개는 하되 revision 비교에서는 뺐다. 처음에 스냅샷을 복제해서 빼는 방식으로 만들었더니 앱이 죽었고, 스냅샷을 만들 때 장치를 넣을지 말지 고르는 쪽으로 바꿨다. 비교에 쓰는 문자열을 만드는 자리가 세 군데 더 있어서 그중 하나라도 다른 기준을 쓰면 revision이 끝없이 올라간다. 실제로 그렇게 됐고, 전부 같은 기준을 쓰도록 맞췄다.

같은 이유로 저장·재개 검사는 `engine.tracks`만 비교한다. 장치는 저장되는 것이 아니고, 다시 열자마자 읽으면 Windows가 아직 입력을 다 세지 않았다.

### 검증

통합 검사가 28개다. 새 검사 하나가 P3 세 가지를 전부 다룬다. 곡선을 화면에서 휘게 만들고 엔진이 그 모양을 연주하는지, 반대로 휘면 반대로 가는지, Undo가 되돌리는지. 노브를 학습시키고 그것이 파라미터를 움직이는지, 다시 연 뒤에도 그런지, 취소한 learn이 아무것도 남기지 않는지. 다른 악기용 프리셋이 무엇을 위한 것인지 말하는지.

실제 MIDI 건반으로 학습시키는 것은 사람이 해야 하며 P2 기록지에 있다.

## 2026-09-11 - P4 UI 폴리싱과 시각적 일관성

`docs/review-next-milestones-v2-2026-09-10.ko.md`의 P4. 전후 스크린샷은 `docs/ui/`에 있다.

### 색을 한 곳에 모았다

같은 뜻의 색이 네 파일에 서른 몇 개의 16진수로 흩어져 있었다. 패널, 선택된 행, 흐린 글자가 파일마다 조금씩 다른 값이었다. `examples/CoCompose/Theme.h`에 이름을 붙여 모으고 손으로 쓴 값 65개를 토큰으로 바꿨다. 남은 것은 파일당 한 개다.

이름을 붙이는 것 자체가 일관성을 만든다. 틀린 토큰은 아홉 군데가 아니라 한 군데에서 틀린다.

색은 charcoal 바탕에 절제된 teal 강조로, 애셋 문서의 제안을 따랐다. 의미가 있는 색(good/warn/danger)은 장식용 색과 구분해 따로 두었다.

### 컨트롤을 벡터로 그린다

`CoComposeLookAndFeel`이 노브·페이더·버튼·콤보박스를 그린다. 전부 코드로 그리므로 배율이 올라가도 흐려지지 않는다.

노브는 아래쪽 90도를 비운 270도 sweep이다. 층은 면 → 외곽선 → 빈 트랙 → 값 arc → 포인터 순이고 포커스가 있으면 링이 하나 더 붙는다. 포인터 끝과 값 arc의 끝은 모든 값에서 일치한다.

애셋 시안의 PAN 노브는 중앙 포인터인데 arc가 왼쪽부터 차 있었다. 문서가 지적한 대로 그건 틀렸다. 범위가 0을 중심으로 대칭인 노브(pan 등)는 중앙에서 값 쪽으로만 채우고, 가운데에 있으면 값 arc가 아예 없다. 시안이 아니라 동작 명세를 따랐다.

페이더는 0dB 자리에 선을 긋는다. 손잡이는 어두운 몸통에 밝은 가운데 선 하나다. 처음에는 손잡이를 밝게 채웠더니 스트립에서 가장 눈에 띄는 것이 손잡이가 돼서 바꿨다. 위치를 읽는 것은 선이지 덩어리가 아니다.

상태는 색으로만 말하지 않는다. hover는 외곽선 명도, pressed는 채움 밝기, focus는 별도 링, disabled는 대비를 낮추되 값의 위치는 그대로 둔다.

### 미터

실제 엔진 측정값으로 그리는 것은 이전과 같지만, 레벨에 따라 색을 바꾸는 대신 구간을 나눠 칠한다. -9dB까지 녹색, -1dB까지 황색, 그 위는 적색이다. 클리핑에 가까워지는 것이 클리핑하기 전에 보여야 한다. 짧게 스쳐 간 피크는 유지선으로 남는다.

## 2026-09-11 - A0 붙인 것은 움직이지 않는다

`docs/ai-chat-milestones.ko.md`의 A0. 아직 아무것도 어디로도 보내지 않는다. 질문이 무엇에 관한 것인지 정확히 말할 수 있게 하는 것, 그리고 그것이 편집으로 오해되지 않게 하는 것이 전부다.

### 패널에 창 제어 세 개

패널마다 최소화·최대화·닫기가 생겼다. 최소화는 헤더를 남긴다. 사라진 패널이 어디로 갔는지 사람이 볼 수 있어야 하기 때문이다. 최대화는 작업 영역을 채우고 같은 버튼이 되돌린다. 닫기는 감추고 View 메뉴가 다시 부른다.

중요한 것은 순서다. 사람이 끌어서 정한 분할 비율을 이 동작들보다 먼저 저장해 둔다. 그래서 복원은 기본 배치가 아니라 그 사람이 만들어 둔 배치로 돌아간다. 패널 크기 조절 자체는 이전과 같고 건드리지 않았다.

닫아 둔 패널도 들고 있던 것을 그대로 유지한다. 채팅 패널에서 이것이 가장 중요하다. 패널을 닫는 것이 대화를 버리는 것으로 읽히면 안 된다.

### 선택은 움직이고 첨부는 움직이지 않는다

`examples/CoCompose/Attachment.h`. 패널의 선택은 다른 곳을 누르는 순간 사라진다. 첨부는 그 반대다. 붙이는 순간 한 번 떠 오고, 그 뒤로는 사람이 어디를 누르든 같은 음악을 가리킨다. 9~16마디에 대한 질문은 답이 도착했을 때도 여전히 9~16마디에 대한 것이어야 한다.

그래서 첨부가 들고 있는 것은 안정된 식별자와 박 범위뿐이다. 패널 상태도, 배열 위치도 들고 있지 않다. 이름은 카드에 보여 주기 위해 함께 적어 두지만 그것으로 무언가를 찾지는 않는다. 같은 이름의 채널이 둘일 수 있고, 첨부한 뒤에 이름이 바뀔 수도 있다.

종류는 셋이다. 편곡 구간(region), 한 패턴 안 한 채널의 노트(notes), 믹서 인서트(insert). 각 카드에는 `Go`·`Update`·`Remove`가 있다. `Go`는 그 음악으로 화면을 옮기고, `Remove`는 뗀다. `Update`만이 첨부가 가리키는 대상을 바꾸며, 그것도 사람이 누를 때만이다. 조용히 따라 움직이는 일은 없다.

첨부는 음악을 복사해 들고 있지 않고 참조만 한다. 그래서 가리키던 것이 지워질 수 있고, 지워지면 카드가 그렇게 말한다. 엉뚱한 곳을 조용히 가리키는 것보다 낫다.

### project_id와 session_id

프로젝트에 실행보다 오래 사는 이름이 생겼다. `session_id`는 이번 실행이 무엇인지를 말하고 앱을 열 때마다 바뀐다. `project_id`는 이 프로젝트가 무엇인지를 말하고 바뀌지 않는다. 세션 파일에 들어 있어 폴더 이름을 바꾸거나 옮겨도 유지된다.

둘을 나눈 이유는 대화를 묶을 대상이 필요해서다. 대화를 실행에 묶으면 앱을 닫을 때마다 처음부터 다시 시작한다.

### chat-inspector.json

채팅이 지금 무엇을 들고 있는지를 프로젝트 옆에 적는다. 화면의 "What gets sent" 다이얼로그와 같은 모양이다. `state.json`처럼 읽기 전용 결과물이며, 쓰기만 하고 다시 읽지 않는다. 첨부는 편집이 아니므로 이 파일이 음악에 영향을 주는 경로는 없다.

### 검증

`tools/test_ai_chat.py`가 다룬다. 세 종류의 첨부, 그리고 붙이기·따라가기·떼기와 모든 패널 제어가 revision을 그대로 두는 동안 실제 편집은 revision을 올린다는 것. `project_id`는 다시 열어도 남고 `session_id`는 남지 않는다는 것. 마일스톤이 지목한 네 경우 — 이름이 같은 채널 둘, 한 패턴의 세 배치, 첨부한 박을 움직이면 안 되는 템포 변경, 첨부가 이름을 들고 있는 사이에 삭제된 대상.

## 2026-09-11 - A0.5 도구 서비스 하나, 안과 밖이 같은 답

`docs/ai-chat-milestones.ko.md`의 A0.5. 사람이 누르는 것이 아닌 모든 읽기가 한 곳을 지난다. `examples/CoCompose/Tools.h`다.

### 왜 한 곳인가

단위를 정하는 자리, 식별자를 푸는 자리, 거절을 이름 붙이는 자리가 각각 하나씩만 있어야 한다. 앱 안의 채팅 패널은 이 서비스를 직접 부르고 밖의 스크립트는 요청 파일을 거쳐 부르는데, 같은 질문에 같은 답이 나오는지를 검사가 확인한다. 거절까지 포함해서다. 조용히 어긋나는 것은 대개 거절 쪽이다.

### 읽기 도구 다섯

| 도구 | 답하는 것 |
|---|---|
| `get_capabilities` | 이 빌드가 실제로 할 수 있는 것, 단위, 상한, 오디오를 보낼 수 있는지 |
| `get_selection` | 지금 선택된 채널·패턴·레인·인서트 |
| `inspect_region` | 두 박 사이에서 재생되는 것과, 그 양옆의 맥락 |
| `inspect_insert` | 인서트의 신호 경로, 효과 순서, 공개 파라미터, 어디로 나가는지 |
| `inspect_pattern` | 한 패턴의 노트와, 그 패턴이 몇 군데에 배치돼 있는지 |

`inspect_region`은 질문받은 구간과 양옆의 맥락을 `clips`와 `context_clips`로 나눠 답한다. 부르는 쪽이 둘을 구분할 수 있어야 하기 때문이다. `inspect_pattern`은 배치 수를 함께 답한다. 그 노트를 바꾸면 모든 배치가 바뀌기 때문이다. `inspect_insert`는 플러그인이 자기 안에 들고 있는 설정은 읽을 수 없다고 명시한다. 파라미터 목록이 전부인 것으로 오해되지 않게 하기 위해서다.

### 쓰기 도구는 목록에 없다

`create_proposal`·`preview_proposal`·`apply_proposal`·`get_operation`·`cancel_operation`은 계약에 이름이 있고 이 빌드에서는 `UNSUPPORTED`로 거절된다. 그리고 `get_capabilities`의 목록에 넣지 않았다.

모델은 있다고 들은 도구를 쓴다. 쓰고 나서 없다는 답을 받는 것이 처음부터 제안받지 않는 것보다 나쁘다. **이 빌드의 AI는 프로젝트를 전혀 바꿀 수 없다.**

### 거절은 문장이 아니라 단어다

`INVALID_ARGUMENT`·`NOT_FOUND`·`STALE_REVISION`·`OUT_OF_SCOPE`·`LOCKED`·`UNSUPPORTED`·`CANCELLED`·`IO_ERROR`. 부르는 쪽은 이 단어로 분기하고, 옆의 문장은 사람이 읽는다. 영어 문장을 파싱해 분기하게 두면 문장을 다듬는 것이 호환성 문제가 된다.

같은 `request_id`를 두 번 물으면 이미 정한 답을 그대로 돌려준다. 시간 초과 뒤 다시 보내는 쪽이 손해를 보지 않는다.

### 스키마와 구현이 따로 놀지 않게

`docs/ai-tool-contract.schema.json`이 계약의 기계가 읽는 쪽이고, `tools/test_tool_contract.py`가 앱의 실제 답을 그 스키마에 대고 검사한다. 문서만 고치거나 코드만 고치면 검사가 걸린다.

### 밖에서 부르는 법

`tool-request.json`을 쓰면 앱이 `tool-response.json`으로 답한다. `control.json`과 같은 모양이다. helper에 명령이 하나 늘었다.

```powershell
python tools/cocompose.py --project '<경로>\project.json' tool inspect_region --arg start_beat=32 --arg end_beat=64
```

helper는 답을 해석하지 않고 앱이 준 것을 그대로 출력한다. 오류도 마찬가지다. 스크립트와 채팅이 서로 다른 이해를 갖게 될 자리를 만들지 않기 위해서다.

### 검증

`tools/test_tool_contract.py`. 앱의 답이 스키마와 맞는지, 잘못된 요청 여덟 개가 계약이 약속한 단어로 거절되며 그중 무엇도 음악을 바꾸지 않는지, 그리고 안과 밖이 같은 질문에 같은 답을 받는지. 통합 검사 28개는 그대로 통과한다. 이 검사는 `jsonschema` 패키지를 쓰므로 다른 검사와 달리 표준 라이브러리만으로는 돌지 않는다.

## 2026-09-11 - A1 프로젝트마다 하나의 대화, 키는 앱 밖에 (완료 아님)

`docs/ai-chat-milestones.ko.md`의 A1. 남의 돈으로 모델을 부르지 않고 갈 수 있는 데까지 갔다. **완료가 아니다.** 판정은 이 항목 끝에 적는다.

### 대화는 프로젝트의 것이다

`examples/CoCompose/Conversation.h`. 질문은 대개 첫 질문이 아니다. "그거 좀 덜 바쁘게"는 앞이 남아 있을 때만 뜻이 있다. 그래서 새 질문은 프로젝트가 이미 갖고 있는 대화에 합류한다.

그 대화는 `project_id`에 묶인다. 실행이 아니라. 앱을 닫는 것, 패널을 닫는 것, 새 질문을 시작하는 것 중 무엇도 대화를 처음으로 되돌리지 않는다. 검사가 재시작을 사이에 두고 세 번 묻고, 세 번째 질문이 첫 번째를 여전히 본다.

`conversation.json`은 프로젝트 안이 아니라 옆에 있다. 대화는 음악이 아니기 때문이다. 메시지를 쓰는 것이 revision이나 undo 이력을 건드려서는 안 되고, 사람이 그것을 읽고 내보내고 지우는 것이 곡에 대해 아무 의미도 갖지 않아야 한다. 새 대화를 시작하면 이전 대화는 지우지 않고 보관한다.

### 앱은 provider와 말하지 않는다

`examples/CoCompose/ChatBridge.h`와 `tools/cocompose_bridge.py`. 앱은 질문을 파일로 적고, 별도의 프로그램이 그것을 집어 답을 적는다. 중요한 순서대로 세 가지 이유가 있다.

키가 이 프로세스에 들어오지 않는다. 프로젝트에도, 대화에도, 로그에도, 크래시 덤프에도 없다. 애초에 여기에 있던 적이 없기 때문이다. 키는 bridge가 환경 변수에서 읽고 bridge 안에만 있다.

어느 provider를 쓰는지가 앱의 문제가 아니게 된다. 다른 bridge가 다른 연결이고, 앱 쪽은 아무것도 바뀌지 않는다.

그리고 느리거나 실패하는 응답이 음악을 붙잡을 수 없다. 메시지 스레드에서 일어나지 않아서가 아니라 이 프로세스에서 일어나지 않아서다. 검사가 transport가 도는 동안 질문을 하나 보내고 재생 위치가 계속 움직이는지 확인한다.

파일 모양은 `control.json`에서 쓰던 것과 같다. `chat-request.json`이 들어가고 `chat-reply.json`이 나오며, `chat-cancel.json`이 중단을 요청하고, `chat-bridge.json`이 무언가 듣고 있는지를 말한다. 반쯤 쓰인 파일은 온전해질 때까지 무시한다.

### 듣는 것이 없으면 거절한다

bridge가 돌고 있지 않으면 질문은 보내지지 않고, 입력란의 글은 그대로 남는다. 오지 않을 답을 기다리게 두는 것보다 낫고, 사람이 용서하지 않는 것은 질문을 다시 타이핑하는 일이다. 취소해도, 실패해도 입력란은 비워지지 않는다. 실제로 질문이 나갔을 때만 한 번 비운다.

### 보내는 것은 도구 서비스가 읽는다

무엇이 첨부됐는지는 A0.5의 도구 서비스를 통해 읽는다. 스크립트가 쓰는 것과 같은 경로다. 그래서 같은 마디에 대해 assistant와 스크립트가 서로 다른 이야기를 들을 수 없다.

**오디오는 보내지 않는다.** bridge의 시스템 프롬프트가 그렇게 말하고, `get_capabilities`의 `audio.can_send_audio`도 `false`다. 소리가 어떤지는 모델이 답할 수 없는 것이므로 답하지 말라고 적어 두었다.

### 판정: A1은 완료가 아니다

**실제 모델이 답한 적이 아직 없다.** echo provider는 모델이 아니고, 모델인 척하지도 않는다. 보내졌을 프롬프트를 그대로 되돌려주면서 매 답변 첫 줄에 자기가 모델이 아니라고 적는다. echo 실행이 실제 실행으로 오해될 방법을 남기지 않기 위해서다. 앱은 어느 provider가 답했는지도 함께 기록한다.

실제 provider로 확인하는 것은 사용자가 직접 할 몫이다.

```powershell
$env:OPENAI_API_KEY = '<키>'
python tools/cocompose_bridge.py --project '<경로>\project.json' --provider openai
```

그 전까지 A1은 열려 있다. P2가 열려 있는 것과 같은 이유다. 빈칸은 통과가 아니라 미검증이다.

### 남은 제한

- 쓰기 도구가 없다. AI는 프로젝트를 바꿀 수 없고, 바꿔 달라는 요청에는 무엇을 어떻게 바꿀지 말로만 답한다.
- 새 대화로 분기하는 것은 아직 `--ui-script`의 `{"chat": "new"}`로만 할 수 있다. 화면에 버튼이 없다.
- provider는 `echo`와 `openai` 둘이다. 스트리밍은 echo에서만 조각으로 나뉘어 오고, openai는 답이 다 온 뒤 한 번에 쓴다.
- 질문하기·첨부하기·패널 조작 중 무엇도 revision과 undo 이력을 건드리지 않는다. 이것은 제한이 아니라 지켜야 할 성질이고, 검사가 그렇게 확인한다.

## 2026-09-11 - A2 제안은 아직 편집이 아니고, 적용은 Undo 하나다

`docs/ai-chat-milestones.ko.md`의 A2. 같은 날의 A0(첨부)·A0.5(도구 서비스)·A1(대화와 bridge) 위에 쓰기 경로를 얹었다. 다만 쓰기는 한 단계로 일어나지 않는다. 제안이 먼저 있고, 적용은 사람이 누른다. 그 사이에 아무 일도 일어나지 않는 것이 이번 작업의 내용이다.

### 제안이라는 물건

`examples/CoCompose/Proposal.h`. 제안은 어떤 노트·파라미터를 **지금 무엇이고 무엇이 될지**까지 함께 들고 있는 데이터다. 만드는 것은 음악을 건드리지 않는다. revision이 오르지 않고 undo 이력에도 남지 않는다.

검사할 것은 셋이고, 각각 **두 번** 검사한다. 만들 때 한 번, 적용하는 순간 다시 한 번이다. 그 사이에 사람이 노트를 옮기거나 템포를 바꾸거나 되돌렸을 수 있다.

- **scope** — 첨부된 것만 건드릴 수 있다. 주변을 읽는 것은 권장이고, 주변을 바꾸는 것은 거절이다.
- **keeps** — "리듬은 그대로"라고 했으면 시작 위치와 길이를 전후로 비교한다. 지켰다는 말을 믿지 않고 잰다.
- **base revision** — 그것을 보고 만든 음악이 움직였으면 `STALE_REVISION`이다. 본 적 없는 음악에 적용하지 않는다.

### 도구 셋이 UNSUPPORTED에서 나왔다

`examples/CoCompose/Tools.h`. A0.5에서 이름만 있던 쓰기 도구 중 `create_proposal`·`get_proposal`·`apply_proposal`이 실제로 동작하고 `get_capabilities`의 목록에 들어갔다. `preview_proposal`·`get_operation`·`cancel_operation`은 여전히 이름만 있고 `UNSUPPORTED`로 거절되며 목록에 넣지 않았다. 있다고 들은 도구를 쓰게 두는 것이 처음부터 없는 것보다 나쁘다는 규칙은 그대로다.

`get_capabilities`에 `writes`가 생겼다. 바꿀 수 있는 것의 전부가 `note.pitch`·`note.start_beat`·`note.length_beats`·`note.velocity`·`note.add`·`note.remove`·`parameter.value`이며, 여기 없는 것은 무엇을 어떻게 요청하든 거절된다. 프롬프트가 아니라 목록이 약속이다.

몇 가지는 코드 쪽에서 정했다.

- 범위는 **첨부에서** 온다. 답변이 스스로 `pattern`·`channel`·`allowed_notes`를 고를 수 없고, 앱이 질문에 붙어 있던 첨부에서 채워 넣는다. 넓혀 달라고 정중히 요청해도 넓어지지 않는다.
- `keeps`에 리듬이 들어 있으면 노트를 더하거나 지우는 것 자체가 `LOCKED`다. 그것도 리듬을 바꾸는 일이기 때문이다.
- 자동화 곡선이 걸린 파라미터는 `LOCKED`다. 저장 값을 써도 들리지 않으므로 성공했다고 답하면 거짓말이 된다.
- 패턴 끝을 넘어가는 노트는 `OUT_OF_SCOPE`다. 들리지 않는 곳에 쓰지 않는다.
- 적용은 이름 있는 트랜잭션 하나다. 무엇을 몇 개 건드렸든 Undo 한 번이다. 두 번 눌러도 두 번 적용되지 않고 `already_applied`로 답한다.

### 화면

`examples/CoCompose/ChatPanel.h`. 답에 변경이 딸려 오면 대화 아래에 블록이 하나 생긴다. 설명과 바뀌는 개수, 그리고 노트별로 `pitch 60 -> 62`처럼 **무엇이 무엇이 되는지**를 최대 여섯 줄 보여 준다. 약속이 아니라 숫자를 보고 사람이 정한다. `Apply change` 버튼은 적용되지 않은 제안이 있을 때만 나타나고, 적용된 뒤에는 `applied`로 바뀌며 버튼이 사라진다. 같은 변경을 버튼으로 두 번 적용할 방법이 없다.

제안이 검사에서 걸리면 같은 자리에 왜 쓸 수 없었는지가 코드와 문장으로 나온다. 조용히 사라지지 않는다.

### 실제 모델은 블록 하나로 제안한다

`tools/cocompose_bridge.py`. 모델은 평소처럼 말로 답하고, 바꾸자고 할 때만 답 맨 끝에 ` ```cocompose-change ` 펜스 블록을 하나 붙인다. 안에는 `description`, `keeps`, 그리고 `notes`(또는 `parameters`)를 담은 JSON 객체가 들어간다. 시스템 프롬프트가 그 모양과 함께 앱이 강제하는 규칙까지 적어 둔다. 첨부된 노트의 ID만 쓸 것, `what`은 `change`·`add`·`remove`, 바꾸는 필드만 적을 것, `keeps`는 결과를 재서 확인하므로 지킬 것만 약속할 것, 그리고 **질문에는 블록 없이 답해도 된다**는 것. 모르겠으면 붙이지 않는 쪽이 옳다고 적어 두었다.

블록이 ID를 쓸 수 있으려면 ID를 본 적이 있어야 하므로, 첨부를 설명할 때 노트마다 음높이·박·길이·세기 옆에 ID를 함께 적는다. 앱은 자기가 건네준 ID만 받는다.

`parse_change`가 답에서 그 블록을 들어낸다. 두 가지를 한다. 사람이 읽을 글에서 JSON을 빼내 대화에는 문장만 남기고, 블록은 손대지 않은 채 앱으로 넘긴다. 무엇이 허용되는지는 여기서 정하지 않는다. 그것은 앱이 첨부·약속·revision에 대고 검사할 일이고, echo가 보낸 것과 모델이 보낸 것이 정확히 같은 검사를 지난다.

블록이 없거나, JSON이 깨졌거나, 바꿀 것이 하나도 없으면 **변경은 없는 것으로 친다.** 반쯤 이해한 편집을 남의 곡에 얹는 것보다 버튼 없는 답이 낫다.

### 믹서 인서트도 첨부가 범위를 준다

파라미터 제안 경로에 세 군데가 어긋나 있었고 전부 고쳤다.

**읽기가 준 ID를 쓰기가 받지 않았다.** `inspect_insert`가 내놓는 효과 ID는 모델의 `EFFECT` uid인데, 파라미터를 찾을 때는 엔진 자신의 item ID로만 찾았다. 자동화 레인이 적어 두는 것은 후자이고 읽기 도구가 손에 쥐여 주는 것은 전자다. `Model::pluginFor`를 새로 두어 **두 이름 중 무엇으로 불러도** 같은 플러그인을 찾게 했다. `automatableParameter`도 이 함수를 지난다.

**범위가 비어 있으면 무엇이든 열려 있었다.** 노트는 첨부가 지목한 패턴과 채널이 울타리 노릇을 하지만 파라미터에는 그런 것이 없다. 그래서 `create_proposal`이 `allowed_inserts`를 읽게 하고, 그 목록이 **비어 있으면 "전부"가 아니라 "하나도"** 로 읽도록 닫아 두었다. 노트 넷에 대한 질문이 페이더를 움직이는 답으로 돌아오는 것을 막는 것은 이 목록뿐이다. `Main.cpp`가 질문에 붙은 첨부에서 목록을 채우는데, 여기서도 노트 첨부 하나를 보고 반복을 끊고 있어 인서트 첨부가 늘 비어 있었다. 둘 다 모으도록 고쳤다.

**적용이 Undo 하나가 아니었다.** 파라미터 값은 트리에 사는 것이 아니라서 `setParameter()`를 그대로 부르면 노트가 들어간 트랜잭션 밖에 남는다. 되돌리면 노트만 돌아오고 페이더는 그 자리에 있었다. 약속이 절반만 참이었다는 뜻이다. 이제 `ParameterAction`으로 같은 트랜잭션에 넣는다. 이 액션은 `LiveProject.h`에 있던 것을 `Model.h`로 옮겨 외부 편집과 제안이 같은 것을 쓰게 했다.

### 내가 낸 회귀 하나, 그리고 그것이 잡힌 방법

ID 두 가지를 다 받아들이게 만든 첫 판은 **빈 문자열까지 받아들였다.** 효과 uid 속성이 없는 플러그인은 그 자리를 `""`로 읽으므로, 아무것도 가리키지 않아야 할 ID가 목록의 첫 플러그인을 가리켰다. 조용히 엉뚱한 것을 찾아 주는 종류라 눈에 띄지 않는다.

`tools/test_live_sync.py`가 잡았다. 고치기 전 바이너리로 세 번 돌려 28/28이 나오는 기준선이 있었는데, 이 변경이 들어간 바이너리에서 **관계없어 보이는 검사 네 개 중 둘이** 깨졌다. 효과 uid 쪽 가지에서 빈 ID를 거절하도록 고쳤고, 그것만 확인하는 검사를 하나 박아 두었다.

### 검증

`tools/test_ai_chat.py`에 A2 검사 두 벌이 들어갔고 전부 통과한다. 하나는 도구 서비스를 직접 부르고, 하나는 사람이 만나는 경로를 지난다. 둘 다 필요하다. 서비스만 맞으면 API지 사용할 수 있는 물건이 아니다.

서비스 쪽에서 확인하는 것:

1. 제안을 만들어도 revision이 오르지 않는다. 그리고 diff가 노트마다 `was`와 `now`를 준다.
2. 첨부 밖의 노트는 `OUT_OF_SCOPE`.
3. 리듬을 지키기로 하고 노트를 옮기면 `LOCKED`. 음높이를 지키기로 하고 바꿔도, 리듬을 지키기로 하고 노트를 더해도 `LOCKED`.
4. MIDI 범위 밖 음높이는 `INVALID_ARGUMENT`, 패턴 밖으로 나가는 노트는 `OUT_OF_SCOPE`, 없는 노트는 `NOT_FOUND`.
5. 그 거절 중 무엇도 음악을 바꾸지 않는다.
6. 적용하면 지목한 음만 바뀌고, 지키기로 한 리듬과 벨로시티는 그대로이며, 첨부 밖의 노트는 하나도 움직이지 않는다.
7. Undo 한 번으로 전부 돌아오고 Redo로 다시 온다.
8. 같은 제안을 다시 적용하면 아무 일도 일어나지 않는다.
9. 오래된 `base_revision`으로 만든 제안은 `STALE_REVISION`이고 다시 시도해도 된다고 답한다.
10. 제안을 만든 뒤 **사람이 템포를 바꾸면** 그 제안의 적용이 `STALE_REVISION`으로 거절되고 음악은 그대로다. 두 번째 검사가 실제로 일을 한다는 뜻이다.

사람 쪽에서 확인하는 것: 노트를 붙이고 묻는다 → 답에 제안이 딸려 오고 아직 적용되지 않은 상태다 → 제안이 대기하는 동안 revision이 그대로다 → `Apply` 한 번에 제안이 지목한 노트만 온음 올라가고 리듬은 유지되며 나머지 노트는 그대로다 → 다시 눌러도 더 바뀌지 않는다 → Undo 한 번으로 전부 돌아온다.

믹서 쪽은 `check_a_mixer_proposal_uses_the_ids_it_was_given`이 본다. `inspect_insert`가 준 효과 ID를 `create_proposal`이 그대로 받는다는 것, 만들어 두는 것만으로는 아무것도 움직이지 않는다는 것, 빈 플러그인 ID는 아무것도 찾지 못하고 `NOT_FOUND`라는 것, 붙인 인서트가 없으면 파라미터 변경이 `OUT_OF_SCOPE`이고 첨부 밖 인서트도 마찬가지라는 것, 적용하면 파라미터가 제안이 말한 값으로 가고 **Undo 한 번으로 되돌아온다**는 것.

블록을 읽는 부분은 `check_a_written_answer_can_carry_a_change`가 따로 본다. 앱도 네트워크도 필요 없는 순수한 검사다. 답 안의 블록이 읽히고, 대화에는 JSON이 아니라 문장이 남고, 블록이 없는 답은 글자 하나 바뀌지 않으며, 반쯤 쓰인 블록도 아무것도 바꾸지 않는 블록도 빈 입력도 변경으로 취급되지 않는다. 모델이 한 말과 앱이 내놓는 버튼 사이에 있는 것이 이것뿐이므로 따로 잰다.

`tools/test_tool_contract.py`도 함께 돈다. 이 검사는 `get_capabilities`가 내놓은 도구를 하나씩 전부 실제로 불러 "그런 도구 없음"이나 `UNSUPPORTED`가 나오지 않는지 본다. 그래서 쓰기 도구를 목록에 넣은 것 자체가 검사 대상이 된다. `writes`가 `note.`·`parameter.` 로만 이뤄지는지도 확인한다. 이 검사만 `jsonschema` 패키지를 쓴다.

통합 검사 28개는 고친 바이너리에서 **세 번 연속** 28/28로 통과한다. 위 회귀 때문에 한 번이 아니라 기준선과 같은 횟수로 돌렸다.

### 남은 제한

- **실제 provider로는 여전히 확인되지 않았다.** 여기서 실제 API를 부른 적이 한 번도 없다. 자동 검사로 증명된 것은 echo bridge, 즉 배선과, 실제 답이 지날 블록 읽기까지다. 그 둘 사이 — 진짜 모델이 규약대로 블록을 쓰는지 — 는 **실연결을 사용자가 직접 확인할 몫이고**, 그 전까지 A1은 열려 있다. **AI 연결이 완료된 것이 아니다.** (이 항목은 아래 "A1 닫힘" 기록에서 닫혔다.)
- echo가 내놓는 변경은 음악적 판단이 아니라 첨부된 노트를 온음 올리는 기계적인 것이다. 모델이 없는 쪽에서 검사·적용 경로를 돌리기 위한 것이지 제안의 본보기가 아니다.
- 바꿀 수 있는 것은 **첨부 안의 노트와 파라미터뿐이다.** 클립 이동, 패턴 생성, 효과 추가, 라우팅 변경은 제안 대상이 아니다. 첨부 밖은 무엇이든 `OUT_OF_SCOPE`다.
- 새 대화로 분기하는 버튼은 여전히 화면에 없다. `--ui-script`의 `{"chat": "new"}`로만 한다. 그때도 이전 대화는 지우지 않고 보관한다.
- `preview_proposal`·`get_operation`·`cancel_operation`은 계약에 이름만 있다.
- laplas 연동은 보류 상태다.
- 실제 청음과 타사 VST3 호환성은 여전히 미검증이다.

## 2026-09-11 - 마일스톤 문서를 실제 빌드에 맞대어 본 결과

작업 기록이 아니라 `docs/ai-chat-milestones.ko.md`의 완료 조건을 한 줄씩 읽고 빌드와 맞대어 봤다. 기록은 한 일을 적은 것이라 안 한 일은 적혀 있지 않다. 다섯 개가 나왔고 전부 조건에 있던 것이다.

### 고스트 노트

A2의 "변경 노트를 고스트 표시하고 원본과 구분". 제안이 오면 피아노롤이 **그 노트가 갈 자리에 윤곽선을** 그린다. 채워진 노트는 존재하는 것이고 윤곽선은 아직 아닌 것이며, 둘을 헷갈리게 두지 않는 것이 이 표시의 전부다.

옮겨지는 노트는 지금 자리에서 갈 자리까지 선을 그어 준다. 그렇지 않으면 노트 두 개로 읽힌다. 지워지는 노트는 몸통을 가로지르는 선을 받는다. 다른 패턴이나 다른 채널에 대한 제안은 엉뚱한 자리에 그리는 대신 **그리지 않는다.** 그리고 그려진 것은 무엇도 클릭·드래그·삭제되지 않는다. Apply를 누르기 전까지 거기에는 만질 것이 없다. 적용되면 표시도 사라진다.

### 패턴 공유 영향

A2의 "패턴 공유 영향이 설명과 일치". 노트 변경은 패턴을 고치는 것이고 패턴은 배치된 자리마다 들린다. 그런데 제안은 "4개 변경"까지만 말하고 나머지는 듣다가 알게 두었다.

이제 제안이 그 패턴의 배치 수를 함께 센다. 패널은 Apply 앞에 **"this pattern is played in N places, and all of them change"** 라고 적는다. 사람이 의도한 변경과 세 번 들리는 변경의 차이가 이 한 줄이다.

### 범위가 프롬프트에 없었다

다섯 중 이것이 제일 컸다. 사람이 노트 넷을 고르면 프롬프트는 그 파트의 서른둘 전부의 ID를 들고 나갔다. 나머지 스물여덟 중 하나를 지목한 제안은 거절된다. **규칙은 지켜졌는데 대화가 성립하지 않았다.** 검사도 통과한다. 거절이 제대로 되니까.

이제 패킷이 `notes_allowed`를 함께 보내고, 프롬프트가 바꿀 수 있는 노트마다 `<- may be changed`를 붙인 뒤 나머지는 맥락이라고 적는다. 전체를 보여 주는 것은 그대로다. 무엇을 고칠지 정하려면 주변을 봐야 하기 때문이고, 선이 어디인지는 말해 주어야 하기 때문이다. echo bridge도 첨부 안에서 고르도록 고쳤다.

### 시작 레시피 다섯

A0.5와 도구 계약이 요구한 "초기 레시피와 재현 검사". `tools/cocompose_recipes.py`에 다섯 개를 두었다. `diagnose-region`, `rewrite-melody`, `tidy-velocity`, `review-insert`, `move-clip`이다.

레시피는 엔진이 아니라 **호출 순서**다. 여기 있는 무엇도 노트가 무엇인지 모르고, ValueTree를 건드리지 않으며, 앱이 하는 검사를 우회할 방법이 없다. 계약이 편집 스크립트 더미 대신 레시피를 요구한 이유가 그것이다. 별도 스크립트는 규칙의 두 번째 구현이고, 두 번째 구현은 두 번째 버그다.

`move-clip`은 `UNSUPPORTED`라고 답한다. 계약에는 있고 이 빌드는 제안할 수 없으므로, 그렇게 말하는 것이 이 레시피의 동작 전부다. 그리고 **무엇도 스스로 적용하지 않는다.** `--apply`를 붙여야 하고, 붙이면 그것이 Undo 하나다.

### pick_notes

마일스톤의 대표 시나리오는 피아노롤에서 노트 몇 개를 골라 그것만 손봐 달라고 하는 것이다. 그 선택은 마우스로만 할 수 있었고, 그래서 **검사가 재현할 수 없는 유일한 시나리오**였다. `--ui-script`에 `{"pick_notes": [<id>, ...]}`를 더해 ID로 고를 수 있게 했다. 빈 목록은 아무것도 고르지 않은 것과 같아 파트 전체를 뜻한다.

### 검사하다 나온 두 가지

패널이 **적용된 뒤에도 제안을 계속 내놓았다.** 다시 그릴지 정하는 값에 제안이 아직 서 있는지가 들어 있지 않아서다. 버튼이 사라지는 것이 화면에만 반영되지 않은 셈이라 두 번째 누르기는 어차피 `already_applied`였지만, 사람에게는 아직 적용되지 않은 것처럼 보였다.

`get_capabilities`는 오디오를 보낼 수 없는 이유를 "아직 연결이 배선되지 않았다"로 적고 있었다. bridge가 들어온 순간부터 사실이 아니다. 진짜 이유는 **이 빌드가 구조를 보내고 녹음은 보내지 않는다**는 것이며, 그렇게 고쳤다. 연결이 없어서 못 보내는 것과 보내지 않기로 한 것은 다른 말이고, 앞의 것은 연결이 생기면 저절로 거짓이 된다.

### 검증

`tools/test_ai_chat.py` 실패 없음. 늘어난 검사는 패널이 최대화된 상태에서도 첨부가 되는지, 골라 둔 노트만 첨부되는지(서른둘 중 셋), 제안이 배치 수를 말하는지, 패널이 어느 제안을 내놓고 있는지 말하는지, 편집기가 그것을 그리는지, 그리고 Apply 뒤에 **둘 다 멈추는지**다.

`tools/test_tool_contract.py` 실패 없음. 다섯 레시피를 실제 검사기에 대고 돌린다. 읽기만 하는 것은 아무것도 바꾸지 않고 들었다고 주장하지 않는지, 제안하는 둘은 각자 다른 것을 약속하는지, `review-insert`가 읽지 못한 부분을 말하는지, `move-clip`이 없다고 말하는지. 그리고 거절 세 갈래를 각각 한 번씩 지난다. 첨부 밖 노트(`OUT_OF_SCOPE`), 깨진 약속(`LOCKED`), 움직여 버린 음악(`STALE_REVISION`). 그 거절 중 무엇도 음악을 바꾸지 않는다.

`tools/test_live_sync.py`는 28/28로 **세 번 연속** 통과한다.

### 남은 제한

- **A1은 그대로 열려 있다.** 여기서 실제 API를 부른 적이 없다. 자동 검사가 증명한 것은 echo bridge와, 실제 답이 지날 블록 읽기까지다. 실연결은 사용자가 직접 확인할 몫이다. **AI 연결이 완료된 것이 아니다.** (이 항목은 아래 "A1 닫힘" 기록에서 닫혔다.)
- 고스트 표시는 피아노롤에만 있다. Playlist와 Mixer에는 제안을 미리 보여 주는 표시가 없다.
- `move-clip`은 레시피 자리만 있고 이 빌드는 그 종류의 변경을 제안할 수 없다.
- 실제 청음과 타사 VST3 호환성은 여전히 미검증이다.

## 2026-09-11 - A1 닫힘: 이 기계에서 도는 모델 하나로 끝까지

`docs/ai-chat-milestones.ko.md`의 A1은 "단일 provider 또는 로컬 외부 agent bridge 하나"를 요구한다. 이 기계에 ollama가 설치돼 있고 모델이 올라와 있으므로, 연결은 **여기서 도는 모델**이 됐다. 로컬 모델도 모델이다. 들고 있을 키가 없고, 기계 밖으로 나가는 것이 없고, 비용이 들지 않는다.

**앞선 두 기록의 "실연결 미검증, 사용자가 직접 확인할 몫"은 이 기록으로 닫힌다.**

### Ollama provider

`tools/cocompose_bridge.py`에 `Ollama`를 더했다. 프롬프트도 계약도 hosted provider와 같고, 다른 것은 키가 없다는 것과 아무것도 나가지 않는다는 것뿐이다. 뒤의 것이 이것을 넣은 이유다. 사람이 붙이고·묻고·읽고·제안받고·적용하는 전 과정을 다 돌려 본 **다음에** 자기 음악을 남에게 보낼지 정할 수 있다.

```powershell
python tools/cocompose_bridge.py --project '<경로>\project.json' --provider ollama --model llama3.1:8b
```

스트리밍한다. 보통 하드웨어에서 도는 로컬 모델은 답이 자라는 것이 보이지 않으면 멈춘 것과 구분되지 않는다. `temperature`는 0.2로 낮춰 두었다. 취향 문제가 아니라, 제안이 JSON 블록이고 자유로워진 모델은 괄호를 틀리기 때문이다.

### 검사는 왜 따로인가

`tools/test_ai_connection.py`를 `test_ai_chat.py`와 **일부러 갈라 두었다.** 뒤의 것은 echo bridge를 쓴다. 답을 미리 알 수 있어야 배선을 검사할 수 있기 때문이다. 그런데 그것은 연결을 검사하는 방법으로는 틀렸다. 연결은 **무슨 말을 할지 알려 주지 않은 쪽이 무언가를 말했을 때** 비로소 확인된다.

그래서 이 검사는 말에 대해 아무것도 단언하지 않는다. 모델이 무엇을 쓰든 성립해야 하는 것만 잰다. 답이 돌아왔는지, 그 답이 **붙인 것에 대한** 답인지, 오디오를 받은 적 없는 모델이 들었다고 말하지 않는지, 두 번째 질문이 첫 번째를 볼 수 있는지, 기다리는 동안 재생이 계속되고 앱이 살아 있는지, 그리고 묻고 답하는 동안 revision이 하나도 움직이지 않았는지.

질문은 마일스톤이 지목한 셋이다. 구간이 이상하다, 이 Insert의 플러그인을 봐 달라, 이 노트들을 설명해 달라. 거기에 아무것도 새로 붙이지 않은 후속 질문 하나를 더한다.

**모델이 없으면 통과하지 않고 종료 코드 2로 끝난다.** echo로 물러나지 않는다. 그렇게 물러나 통과하는 것이 바로 마일스톤이 경고하는 거짓 보고다.

### 결과

`llama3.1:8b`로 두 번 돌렸고 두 번 다 실패 없음이다. 실제로 받은 답:

> The mixer insert is 'Insert 1 CoCompose Synth'. It has a gain of 0.00 dB and a pan of 0.00. It's not using any effects, and it's being fed by the 'CoCompose Synth' channel.

그리고 아무것도 새로 붙이지 않은 후속 질문에:

> The highest note is the one with a pitch of 72.

A2도 echo가 아니라 **실제 모델로** 확인됐다. 모델이 변경 블록을 직접 썼고, 앱이 그것을 검사했고, Apply가 모델이 지목한 노트 넷만 정확히 움직였다. 리듬은 유지됐고 첨부 밖은 하나도 건드려지지 않았다.

### 실제로 물어보니 나온 문제 둘

**닫는 펜스가 오지 않았다.** 첫 모델이 블록을 열고, 온전한 JSON 객체를 다 쓰고, 마지막 백틱 세 개를 쓰지 않았다. bridge는 멀쩡한 변경을 구두점 셋 때문에 버렸다. 이것이 **가장 흔한 실패 방식이지 예외가 아니다.** 실제 모델에게 던진 맨 첫 질문에서 나왔다. `parse_change`가 이제 중괄호를 세어 객체의 끝을 찾고, 문자열 안의 중괄호는 건너뛴다. 닫는 펜스는 있으면 먹고 없어도 된다. 완결돼야 하는 것은 펜스가 아니라 객체다. 검사 네 개로 박아 두었다. 펜스 없는 블록이 읽히는지, 그 앞의 문장이 멀쩡히 남는지, 문자열 안의 중괄호가 객체를 일찍 끝내지 않는지, 중간에 끊긴 객체는 변경이 아닌지.

**범위 설명을 대충 읽고 넘어갔다.** 노트 넷을 붙였는데 모델이 파트 전체를 지목했다. 거절은 정확히 됐다. 그런데 **사람이 요청한 적 없는 거절은 대화가 아니다.** 이제 바꿀 수 있는 노트 ID를 한 줄에 그것만 따로 적는다. 노트마다 붙는 표시는 그대로 두고, 그 아래에 목록을 한 번 더 평범한 문장으로 말해 준다. 그 뒤로는 모델이 범위 안에 머물렀다.

### 남은 제한

- **hosted OpenAI 경로(`--provider openai`)는 여기서 한 번도 돌려 본 적이 없다.** 확인된 것은 로컬 ollama 경로뿐이다. 코드는 같은 모양이지만 돌려 보지 않은 것은 돌려 보지 않은 것이다.
- **작은 로컬 모델은 음악적 판단을 믿을 것이 못 된다.** "up one tone"을 반음 하나로 읽었다. 앱의 약속 — 범위, 지키기로 한 것, Undo 하나 — 은 그와 무관하게 지켜졌고 그것이 요점이다. 음악의 질은 주장하지 않는다.
- 고스트 표시는 여전히 피아노롤에만 있다.
- 실제 청음과 타사 VST3 호환성은 여전히 미검증이다.

## 2026-09-11 - 연결이 스스로에 대해 거짓말한 네 가지, 그리고 룰러와 우클릭

커밋 둘이다. `da88185`는 3차 리뷰(`docs/review-milestones-v3-2026-09-11.ko.md`)의 C1~C4, `1185b30`은 조작 명세(`docs/daw-interaction-spec.ko.md`)의 D0와 D1이다. 공통점은 **여섯 개 전부 동작하는 것처럼 보이던 것**이라는 점이다. 검사도 통과하고 있었다.

### C1 답한 것을 기억하는 자리가 프로세스였다

bridge가 무엇에 답했는지는 메모리의 set에 있었다. set은 프로세스만큼 산다. 그래서 질문이 아직 남아 있는 폴더에서 bridge를 다시 켜면 **그 질문이 provider로 한 번 더 나갔다.** 요금이 한 번 더 나가고, 앞의 답이 뒤의 답으로 덮이고, 쓰기 도구가 붙는 날에는 편집이 한 번 더 일어난다.

이제 기록은 요청 옆의 답 파일이다. 파일은 프로세스보다 오래 산다. 같은 request ID에 `ok`나 `error`가 이미 적혀 있으면 그 질문은 끝난 질문이다.

답이 **오다가 끊긴 경우는 조용히 다시 보내지 않는다.** provider가 일을 했는지 — 했다면 요금도 나갔는지 — 는 이쪽에서 알 방법이 없다. 알 수 없는 것을 추측해서 재시도하는 것과 사람에게 말하고 결정을 넘기는 것 중에 뒤를 골랐다. 답 자리에 "bridge가 답을 받는 도중에 멈췄다, 아무것도 바뀌지 않았다, 원하면 다시 물어라"가 적힌다.

### C2 죽은 bridge가 살아 있다고 말하고 있었다

`chat-bridge.json`의 `ready: true`는 **시작할 때 한 번** 적히는 값이었다. 정상 종료는 그것을 지우지만, 강제 종료된 프로세스는 아무것도 지우지 못한다. 남은 파일은 존재하지 않는 프로그램의 약속이고, 앱은 그것을 믿었다. 그 상태에서 질문을 보내면 입력란의 글자는 사라지고 답은 영원히 오지 않는다.

이제 instance id가 있고, **2초마다 heartbeat를 적는다.** 적는 쪽은 별도 스레드다. provider 호출이 진행 중인 동안에도 뛰어야 하기 때문이다 — 그때가 bridge가 죽은 것과 가장 비슷해 보이는 순간이다. 앱의 `isConnected()`는 박동이 **여러 번** 빠졌을 때 죽었다고 본다. 한 번은 부하 걸린 기계에서도 빠지고, 그것으로 죽었다고 하는 편이 1초 더 기다리는 것보다 나쁘다.

사라진 bridge로 나간 질문은 기다림을 끝내고 **사람이 쓴 글자 그대로 입력란으로 돌아온다.** 백그라운드 프로세스가 죽었다는 이유로 질문을 다시 타이핑하게 만드는 것은 사람이 용서하지 않는 종류의 일이다. 막 켜진 bridge가 아직 아무것도 적지 않은 틈이 있으므로 6초의 유예를 둔다.

### C3 대화는 전부 저장하고 일부만 보냈다

`recentForContext`가 넘기는 것은 `from`과 `text`뿐이었다. 그래서 "그 부분 덜 복잡하게"라는 후속 질문은 **가리킬 대상 없는 지시대명사**로 모델에 도착했다. 대화는 온전히 디스크에 있었고, 모델이 받는 대화만 달랐다.

이제 이전 메시지의 첨부가 함께 간다. 종류, ID, 노트 수, 박 범위, 그리고 **어느 revision에서 읽은 것인지**다. 마지막 것이 핵심이다. 프롬프트는 그때 얼어붙은 모습으로 대상을 설명하고, 그 뒤로 음악이 움직였으면 움직였다고 적는다. 지금도 그 모습이라고 단언하지 않는다.

자르는 것은 여전히 자르되 **잘랐다고 말한다.** 사람이 내건 조건은 보통 문장 끝에 있고, 조용한 절단이 가져가는 것이 정확히 그 부분이다.

### C4 클립 이름과 길이는 음악이 아니다

구간 첨부는 클립 이름·시작·길이만 문자열로 보냈다. 둘 다 "Pattern 2"고 둘 다 16박인 두 클립은 — 하나가 베이스 라인이고 하나가 클러스터 코드여도 — **똑같이 읽힌다.** 그 상태로 "이 구간 뭐가 이상하냐"를 받은 모델이 할 수 있는 것은 추측이고, 진단처럼 보이는 추측이 이 경로가 낼 수 있는 최악이다.

`describeClip`이 이제 노트를 함께 싣는다. 무한정은 아니고 **구간 전체가 나눠 쓰는 예산**이며, 구간 본체가 먼저 쓰고 주변 문맥이 남은 것을 쓴다. 곡이 빽빽할 때 얇아지는 쪽은 물어본 것이 아니라 그 주변이어야 한다. 못 실은 노트는 세어서 적는다. 빠진 것이 있다는 것을 아는 쪽은 더 물어볼 수 있다.

Insert는 **sends를 적는다.** 센드는 무언가가 놓인 적 없는 자리에서 들리는 이유이고, 그것을 빼고 쓴 설명은 자신 있게 틀릴 수 있다. 파라미터는 12개까지 이름을 적고 나머지는 **몇 개를 적지 않았는지** 말한다.

### D0 룰러는 한 가지만 했고 그것은 셋 중 제일 쓸모없는 것이었다

룰러 클릭은 그 자리에 길이 0의 루프를 잡았다. 마우스로 "여기서부터 틀어 봐"라고 말할 방법이 없었다.

- **좌클릭은 seek다.** 스냅은 걸지 않는다. 편집 격자는 별개의 문제이고, 곡의 한 순간을 가리키는 사람은 그 순간을 뜻한다.
- **드래그는 미리 보여 주고 손을 뗄 때 한 번 seek한다.** 지나가는 모든 위치로 seek하는 것이 stuck note와 끊김을 만드는 방법이다.
- **루프 핸들 드래그는 잡은 쪽 끝만** 움직인다. 반대쪽을 지나가면 뒤집힌 루프가 아니라 시작과 끝이 바뀐다.
- **Shift+드래그는 시간 범위를 표시한다.**

시간 범위는 루프도 아니고 클립 선택도 아닌 **세 번째 것**이다. "곡의 이 부분"이라는 뜻이고, 질문이 보통 그것에 대한 것이다. 그래서 자기 색으로 따로 그리고, 아무것도 고르지 않았을 때 **AI가 붙이는 것이 이것이다.** 붙이는 순서는 선택한 클립 → 표시한 범위 → 루프다. 루프는 어제부터 거기 있었을 수 있는 재생 설정이므로 제일 뒤다. 범위를 긋는 것과 클립을 고르는 것은 **서로를 지운다.** 둘 다 "이 부분"을 말하는 방법이고, 남아 있는 쪽이 조용히 이기게 두면 방금 범위를 그은 사람의 질문이 몇 분 전에 고른 클립에 붙는다.

### D0 Stop이 자기 명령이 됐다

Play/Stop은 토글이라 "재생을 시작한 자리로 데려다 달라"를 말할 수 없다. 멈춰 있을 때 누르면 재생이라는 뜻이기 때문이다. Stop을 따로 떼어 냈고, **이미 멈춰 있을 때 다시 누르면 마지막으로 재생을 시작한 자리로 돌아간다.**

Transport 키는 텍스트 상자에 키보드가 있으면 **물러난다.** 채팅에 질문을 쓰다가 누른 Space는 공백이고 Home은 줄 처음이다. 물러나는 것은 처리한 것으로 친다. 처리하지 않았다고 답하면 키가 다른 곳으로 흘러가기 때문이다.

`sync-status.json`에 `position_beats`, `loop_start_beat`, `loop_end_beat`가 생겼다. 엔진은 초로 세고 룰러는 박으로 그려져 있는데, 룰러를 검사하는 쪽이 템포 계산을 해야 하는 것은 이상하다.

### D1 우클릭은 이제 묻는다

클립 우클릭은 삭제였다. 노트 우클릭도 삭제였다. **일어나기 전에 되돌릴 수 없는 유일한 제스처**이고, 빗나간 클릭 하나가 클립 하나였다. 다른 DAW가 전부 "이걸로 뭘 할 수 있냐"를 묻는 데 쓰는 제스처이기도 하다.

| 대상 | 메뉴 |
|---|---|
| 클립 | 피아노롤 열기 / 복제 / Make unique / 분할 / AI에게 묻기 / 삭제 |
| 노트 | 반음·옥타브 위아래 / 퀀타이즈 / AI에게 묻기 / 삭제 |
| 빈 격자 | 선택한 패턴 놓기 / 표시한 범위를 루프로 / 범위 지우기 / AI에게 묻기 |

**선택 안을 우클릭하면 선택이 유지된다.** 명령은 골라 둔 전부에 가고 Undo 하나로 돌아온다. 선택 밖을 우클릭하면 가리킨 것으로 옮겨 간다. 그것이 사람이 뜻한 것이다.

메뉴 항목은 이미 있는 명령을 부른다. 메뉴와 단축키와 메뉴 바가 서로 다른 말을 할 수 없는 이유가 그것이다. 그리고 **메뉴가 열려 있는 동안 곡은 가만히 있지 않는다** — 스크립트가 지울 수도 있고 도착한 답이 바꿀 수도 있다. 그래서 콜백은 대상을 기억하지 않고 메뉴가 닫힌 시점에 다시 찾는다. 없으면 아무것도 하지 않는다.

삭제는 그대로 삭제된다. `Delete` 키로.

### 검증

넷 중 셋은 네트워크가 아니라 **provider spy**를 쓴다. 일부러 그렇게 했다. 유료 API가 있어야 도는 검사는 **돌지 않는 검사**다.

`tools/test_ai_chat.py`, `tools/test_tool_contract.py`, 실제 모델에 대한 `tools/test_ai_connection.py` 전부 실패 없음. `tools/test_live_sync.py`는 이 바이너리에서 28/28로 세 번 연속 통과했다.

### 확인하지 못한 것 하나 — 통과가 아니다

**"텍스트 입력 중 Space가 재생을 시작하지 않는다"는 이 기계에서 자동으로 확인할 수 없다.** 가드는 JUCE가 키를 실제로 배분할 때 보는 것과 같은 포커스를 읽으므로 실사용에서는 맞다. 그러나 이 기계는 스크립트에게 앱 창의 키보드를 내주지 않아서 **가드가 존재하는 이유인 그 상태를 만들어 낼 수가 없다.**

`test_daw_interaction.py`는 이것을 통과에도 실패에도 넣지 않고 `NOT CHECKED HERE`에 적는다. 통과로 적으면 거짓 보고이고, 실패로 적으면 코드가 아니라 방을 탓하는 것이다. **사람이 채팅 입력란에 타이핑하면서 Space를 눌러 확인할 몫이다.**

### 남은 제한

## 2026-09-12 - 더블클릭은 여는 것이고, Select가 먼저이고, 설명되지 않던 실패의 설명

커밋 둘이다. `7e6ffd4`는 조작 명세(`docs/daw-interaction-spec.ko.md`)의 D2, `a02af99`는 D3과 D4의 첫 조각이다. 뒤의 것에는 이 프로젝트가 오랫동안 **"설명되지 않은 간헐적 실패"로 적어 온 것의 설명**도 들어 있다.

### D2 더블클릭이 자르고 있었다

클립 더블클릭은 그 자리에서 클립을 **잘랐다.** 자르기는 작정하고 하는 일이고 그것을 위한 도구와 명령(`Ctrl+E`, 클립 메뉴의 분할)이 이미 따로 있다. 반면 **"이 안의 노트를 좀 보자"에 해당하는 마우스 제스처는 하나도 없었다.** 처음 앱을 여는 사람이 제일 먼저 해 보는 것이 그것인데도 그렇다.

이제 더블클릭은 연다. 쌍의 **첫 클릭이 이미 그 클립을 골라 놓았고** 그것이 정확히 여는 데 필요한 것이므로, 이 경로로 들어가도 뒤에 남는 것이 없다. 검사는 더블클릭 뒤에 클립 수가 그대로이고 revision이 오르지 않는지를 함께 본다. **여는 것은 편집이 아니다.**

### D2 여는 것이 버튼 하나였다

에디터를 여는 방법은 Channel Rack의 `Piano roll` 버튼뿐이었다. 명령이 아니었으므로 **단축키도, 메뉴 항목도, 대상 메뉴가 부를 것도 없었다.** D1에서 만든 클립 메뉴의 '피아노롤 열기'조차 부를 명령이 없었다.

이제 `Piano roll`은 명령이다. 더블클릭, `Enter`, 클립 우클릭 메뉴가 전부 이 하나를 지나간다. Rack 버튼은 같은 함수를 직접 부른다.

선택한 채널이 여는 패턴에서 연주하지 않으면 **그 패턴이 실제로 연주하는 채널로 옮겨 간다.** 드럼 클립을 열었는데 베이스의 빈 격자가 나오는 것은 여는 사람이 뜻한 것이 아니다. 다만 이 대체는 **보려고 열 때만** 켜진다. 노트를 쓰면서 여는 경로(`addPianoRollNote`)에서는 꺼져 있다. **아직 파트가 없는 채널이야말로 지금 그 파트를 만드는 중인 채널**이고, 쓰기가 다른 곳으로 돌려지면 안 되기 때문이다. 이 구분을 잡아낸 것은 live-sync였다. **세 번 돌려 세 번 같은 검사가 실패했고, 멜로디가 엉뚱한 채널에 얹혔다.**

### D2 편집이 어디까지 닿는지 창이 먼저 말한다

한 패턴이 편곡의 두 곳에 놓여 있으면 노트 편집은 **두 곳 모두에서 들린다.** 클립 하나를 더블클릭해서 들어온 사람은 당연히 그 클립을 고치고 있다고 생각한다.

그래서 에디터 제목줄이 패턴 이름, 채널 이름, 그리고 몇 군데에서 연주되는지를 적는다 — `played in 2 places, and editing changes all of them`. 한 곳이면 `played in one place`, 아직 안 놓였으면 `not placed in the song yet`이다. 그리고 **창이 열려 있는 동안 계속 다시 센다.** 열어 둔 사이에 누가 같은 패턴을 한 번 더 놓을 수 있고, 그때 제목줄이 옛말을 하고 있으면 없느니만 못하다. 검사는 배치를 하나 더 놓고 제목줄이 `2 places`로 바뀌는지를 **아무것도 편집하기 전에** 본다.

### D2 Select가 그리기를 멈췄다

피아노롤에서 빈 격자를 누르면 **노트를 쓰면서 동시에 선택 상자를 시작했다.** 그래서 사각형 선택을 하려고 드래그할 때마다 **노트가 하나 남았다.** 두 일을 한 제스처가 하고 있었고 어느 쪽도 제대로 하지 못했다.

Select와 Draw를 툴바에 이름으로 갈라 놓았고 쓰는 것은 Draw뿐이다. 빈 격자 우클릭 메뉴에서도 도구를 고를 수 있고 두 곳은 서로를 갱신한다. 기본은 Draw로 두었다 — 노트 편집기는 노트를 쓰러 여는 곳이다.

건반 미리듣기는 **창이 키보드를 잃으면 소리를 끈다.** 누른 채로 포커스가 떠나면 note-off를 가져올 mouse-up이 다른 데로 가 버려서, 그 음은 영원히 났다.

그 밖에 다른 것을 보다가 발견한 알림 폭풍 하나. follow-playhead 타이머가 **뷰가 움직인 모든 이유를 사람이 스크롤한 것으로** 쳤다. 멈춰 있는 동안 리레이아웃 한 번이 "따라가기 중단"과 그 해제를 같은 tick에 알렸고, 초당 열두 번 그랬다. 스크롤이 "여기 두라"는 뜻인 것은 **무언가 재생 중일 때뿐이다.**

### D3 편곡도 Draw가 항상 켜진 것처럼 굴고 있었다

Playlist는 빈 곳을 누르면 선택한 패턴을 **놓았다.** 그래서 구간을 드래그로 고르면 클립이 하나 남았고, 선택하는 유일한 방법은 modifier(Alt)를 잡는 것이었다.

이제 **Select가 기본이다.** 어느 편곡 뷰에서나 그렇듯이 놓는 것은 고르는 일이다. 툴바의 도구 상자와 빈 격자 우클릭 메뉴 둘 다에서 고르며, **한쪽이 다른 쪽을 설정하므로 둘이 다른 말을 할 수 없다.** 앱이 지금 무슨 도구를 들고 있는지는 `chat-inspector.json`의 `grid_tool`에 나온다.

### D3 그래서 Alt가 비었고, 스냅을 치우는 자리가 됐다

Alt는 여기서 사각형 선택이었다. 그 일은 이제 Select 도구가 제대로 하므로 modifier가 비었다. Alt는 **누르고 있는 동안 스냅을 멈춘다.** 대부분의 편곡에서 그것이 Alt의 뜻이다 — 격자를 잠깐 치워라, 여기가 어디인지 내가 안다.

**피아노롤의 Alt는 그대로 velocity 드래그다.** 명세가 요구하지 않는 일관성을 사기 위해 오래된 손버릇을 깨는 것은 나쁜 거래다. 두 창이 서로 다른 도구를 가진 서로 다른 창이고, **어긋나는 지점은 조용히 맞추는 대신 적어 둔다.** 이 문서와 사용 설명서에 적힌 것이 그 기록이다.

### D3 휠 규약은 이제 두 창에서 하나다

휠은 세로 스크롤, Shift+휠은 가로, **Ctrl+휠은 포인터를 중심으로 한 줌**이다. 피아노롤에는 **휠 처리가 아예 없었다.**

중심이 핵심이다. 폭만 바꾸면 줌은 왼쪽 끝을 중심으로 돌고, 그러면 **보고 있던 것이 매번 화면 밖으로 밀려난다.** "화면이 자꾸 도망간다"는 느낌의 전부가 그것이다. 지금은 포인터 아래 있던 박이 포인터 아래 남는다.

### D3 맞춤 줌 셋

전체 곡 맞춤, 선택 맞춤, 이전 줌으로 복귀. 편곡의 끝을 휠로 찾아다니는 것은 사람이 **앱을 그만 쓰는 방식으로** 그만두는 종류의 일이다. 선택 맞춤은 눈금자에 표시한 시간 범위를 먼저 보고, 없으면 골라 둔 클립들의 범위를 쓴다. 둘 다 없으면 맞추는 대신 **무엇을 고르라고 말한다.** 복귀는 맞추기 직전의 줌과 가로 스크롤을 되돌린다.

셋 다 명령으로 등록되어 있고 범주는 View다. 다만 **메뉴 바의 View 메뉴에는 아직 항목으로 얹지 않았다.** `Piano roll`도 Edit 메뉴에 없다. 이름으로 부르는 경로(`--ui-script`의 `{"command": "Fit whole song"}`)와 대상 메뉴·단축키로는 닿지만, **메뉴를 열어 눈으로 찾을 수는 없다.** 다음에 할 일이다.

### D3 자동화 점이 마지막까지 우클릭으로 지워지고 있었다

D1에서 클립과 노트의 우클릭 삭제를 없앴을 때 **자동화 곡선의 점만 남았다.** 직전 기록의 '남은 제한'이 D1을 절반이라고 적은 그 절반 안에 이것이 있었다. 같은 이유가 그대로 적용된다 — **일어나기 전에 되돌릴 수 없는 유일한 제스처**다. 이제 곡선 줄의 우클릭은 좌클릭과 같은 일(점 고르기·만들기)을 하고, 점은 `Delete`로 지운다.

### D4 노브와 페이더에 사람이 기대하고 오는 두 제스처

**더블클릭은 기본값으로 되돌리고, 우클릭은 숫자를 묻는다.** 정확히 -6 dB를 원하는데 컨트롤이 스무 픽셀 폭이면 드래그는 가망이 없다. 둘 다 취향이 아니라 **모든 믹서가 하는 일**이고, 없으면 아무리 잘 그려도 미완성으로 읽힌다.

`Theme.h`의 새 `ValueSlider`가 그것이며 Channel Rack의 볼륨·팬과 Mixer의 페이더·팬이 평범한 `Slider` 대신 이것을 쓴다. 이름을 `Knob`이 아니라 `ValueSlider`로 한 이유가 있다 — **믹서의 페이더는 노브가 아니고, 숫자 입력이 가장 필요한 것이 바로 그것이다.** 기본값은 슬라이더 범위의 시작이 아니라 **그 컨트롤이 설정된 값**(볼륨 0 dB, 팬 중앙)이므로 "기본으로"가 프로젝트가 뜻하는 기본을 뜻한다.

입력 상자를 **비워 두거나 숫자가 아닌 것을 넣으면 아무 일도 일어나지 않는다. 0이 아니다.** 게인 컨트롤에서 0은 아무도 요청하지 않은 편집이고, 무엇보다 **소리 없이** 일어나는 편집이다.

### D4 채널을 고르면 믹서가 따라온다

Channel Rack에서 채널을 고르면 **그 채널이 흘러 들어가는 인서트가 함께 선택된다.** 베이스를 누르고 믹서를 본 사람은 베이스를 보고 있을 것이라 기대한다. 매번 눈으로 스트립을 찾게 만드는 것이 믹서를 별개의 프로그램처럼 느끼게 하는 작은 마찰이다.

### 설명되지 않던 실패는 앱이 아니라 검사에 있었다

`test_live_sync.py`의 `check_render_output_is_never_lost`가 내던 **"Nothing was edited while the render ran"** 는 이 프로젝트의 여러 기록에 "원인을 모르는 간헐적 실패"로 적혀 있다. **앱이 아니라 검사가 틀렸다.**

루프가 이랬다.

```python
while read(sub / "render-status.json").get("running") is not False:
```

렌더가 **첫 읽기보다 먼저 끝난 기계에서는 루프 본문이 한 번도 돌지 않는다.** `edits`는 0으로 남고, 마지막 줄의 `assert edits > 0`이 실패한다. 실패 메시지는 "렌더가 도는 동안 아무것도 편집되지 않았다"였고, 그것은 **기계가 빨랐던 것을 앱 탓으로 돌리는 문장**이다. 검사가 재고 싶었던 것(렌더 중 편집이 렌더 결과를 망치지 않는다)과 검사가 실제로 요구한 것(편집이 렌더와 겹쳤다)이 달랐다.

이제 편집은 **항상 시도하고**, 그것이 렌더와 겹쳤는지는 **요구하는 대신 기록한다.** 겹침은 기계 속도에 달린 것이고 검사가 통제할 수 없는 것을 단언하면 안 된다. 고치기 한 시간 전에는 **세 번 중 두 번이 실패**하고 있었고, 고친 뒤 **세 번 중 세 번이 28/28**이었다.

직전 기록을 포함해 이 실패를 "설명되지 않은 것"으로 적은 항목들은 고쳐 쓰지 않고 이 절을 가리키는 한 줄만 붙였다. **당시에 모르던 것은 실제로 몰랐던 것이 맞다.**

### 검증

`tools/test_daw_interaction.py` 실패 없음. D2로 세 절(더블클릭이 자르지 않고 열며 revision을 올리지 않는지, 제목줄이 배치 수를 말하고 두 번째 배치에서 바뀌는지, Select가 노트를 쓰지 않고 Draw가 쓰는지), D3으로 두 절(Select가 클립을 놓지 않고 Draw가 놓는지, Alt를 잡은 드래그가 격자 사이에 떨어지는지)이 늘었다. 전부 실제 `MouseEvent`를 핸들러에 넣는다.

`tools/test_ai_chat.py`, `tools/test_tool_contract.py`, `tools/test_chat_reliability.py` 실패 없음. `tools/test_live_sync.py`는 28/28로 **세 번 연속** 통과했고, 이번에는 그것이 재현되지 않은 것이 아니라 **원인을 고친 뒤의 결과다.**

D2 검사들은 follow-playhead 타이머 수정 이전 빌드에서 돌았고, 그 수정은 어느 검사도 지나가지 않는 타이머의 몇 줄이다. D3 커밋에서 전부 다시 돌렸다.

### 남은 제한

- **D3이 요구한 것 중 안 한 것**: Erase·Split 도구(분할은 여전히 명령과 클립 메뉴로만), 가운데 버튼 드래그 pan, 드래그 중 가장자리 자동 스크롤, 레인 높이 조절.
- **D4가 요구한 것 중 안 한 것**: FX 더블클릭으로 플러그인 창 열기, Browser의 클릭(선택)·preview(청음)·드래그(배치) 구분, 단축키 충돌표.
- **D1은 여전히 절반이다.** 우클릭 메뉴가 있는 곳은 클립·노트·빈 격자 셋이다. 레인/채널 헤더, Insert/FX 슬롯, 노브/페이더, 오디오 클립에는 없다. 노브·페이더는 이번에 우클릭이 생겼지만 그것은 값 입력 메뉴이지 명세가 요구한 자동화·MIDI learn까지 있는 대상 메뉴가 아니다.
- `Piano roll`과 맞춤 줌 셋은 **명령일 뿐 메뉴 바에 없다.**
- **"텍스트 입력 중 `Space`"는 여전히 이 기계에서 자동으로 확인되지 않는다.** 스크립트에게 앱 창의 키보드를 내주지 않기 때문이다. `test_daw_interaction.py`는 이것을 통과에도 실패에도 넣지 않고 `NOT CHECKED HERE`에 적는다. 사람이 채팅 입력란에 타이핑하면서 눌러 확인할 몫이다.
- **hosted OpenAI 경로(`--provider openai`)는 여기서 한 번도 돌려 본 적이 없다.** 확인된 것은 로컬 ollama 경로뿐이다.
- 고스트 표시는 여전히 피아노롤에만 있다. 실제 청음과 타사 VST3 호환성도 여전히 미검증이다.
