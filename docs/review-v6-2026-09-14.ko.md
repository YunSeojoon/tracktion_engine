## 발견 사항

### R1 · P1 — 선택한 후보를 들어도 Apply는 다른 제안을 적용한다

위치: `examples/CoCompose/ChatPanel.h:60`, `:262`, `:467`.

같은 revision에서 서로 다른 제안 두 개를 받은 뒤 후보 목록에서 첫 번째를 고른다. Preview는 `chosenProposal()`을 사용해 첫 번째를 렌더하지만 Apply는 `offered`를 사용한다. `offered`는 대화를 순회하며 마지막 미적용 제안으로 정해지고, 후보 선택의 onChange는 레이아웃만 갱신한다. 변경 설명 역시 선택 후보에 맞춰 바뀌지 않는다.

따라서 첫 번째 후보를 듣고 Apply를 누르면 두 번째 제안이 적용될 수 있다. 둘의 base revision이 같으면 stale 검사가 이 오류를 막지 않는다.

수정: 선택 후보 ID를 diff·Preview·Apply의 공통 대상으로 삼고 적용 가능 상태도 같은 대상으로 계산한다. 후보 선택은 음악을 변경하지 않아야 한다.

회귀 조건: 같은 revision의 서로 다른 두 후보 → 첫째 선택 → 설명/Preview/Apply ID 일치 → 실제 노트 readback이 첫째 결과 → 한 번 Undo. 최신 후보 적용만 확인하는 검사로 대체하지 않는다.

### R2 · P1 — 새 비교가 완성되기 전에 이전 비교 파일을 재생할 수 있다

위치: `examples/CoCompose/Main.cpp:1955`, `:2238`, `:2030`.

한 번 비교한 뒤 다른 제안으로 Preview를 시작한다. A/B는 계속 동일한 `preview-before.wav`, `preview-after.wav` 경로에 쓰고, 재생 버튼의 준비 상태는 두 파일의 존재 여부만 검사한다. 렌더 중인지, 두 파일이 같은 제안·revision의 완료된 결과인지 검사하지 않는다. `listenToHalf`에도 해당 검사가 없다.

첫 번째 렌더가 교체된 뒤 두 번째 렌더가 끝나기 전에는 새 A와 이전 B가 존재한다. 이때 재생 버튼을 누르면 서로 다른 비교의 파일을 듣는다. B 렌더 실패 뒤에도 파일이 남아 있으면 같은 문제가 지속된다. 파일 하나의 원자적 교체는 A/B 쌍의 일관성을 보장하지 않는다.

수정: 두 렌더가 성공한 비교에 proposal ID·revision·범위를 함께 묶어 게시하고 그 비교만 재생 대상으로 삼는다. 새 비교 중 이전 것을 허용한다면 이전 비교라는 표시와 파일 분리가 필요하다. 최소 수정은 시작/실패 시 재생을 비활성화하고 양쪽 성공 후에만 활성화하는 것이다. 재생 중인 파일을 교체하는 경로도 정리한다.

회귀 조건: 첫 비교 완료 → 둘째 비교 시작 → A 완료/B 대기 및 B 실패 각각에서 혼합된 쌍 재생 불가. 파일이 존재한다는 조건만으로 통과시키지 않는다.

### R3 · P2 — Insert 제안의 Preview는 해당 Insert가 연주하지 않는 구간을 고른다

위치: `examples/CoCompose/Main.cpp:2168` (`previewFromThePanel`), 특히 `:2214`.

패널의 범위 추론은 노트 변경과 클립 변경만 살핀다. 파라미터/이펙트/Send만 바꾸는 제안은 무조건 0~8박으로 떨어지고 문맥 여백을 붙인다. 예를 들어 33박부터 들어오는 악기의 Insert를 첨부하고 효과를 바꾸면, Preview는 그 악기가 없는 곡 도입부를 렌더한다. 사용자가 비교 구간을 고르는 UI도 이 경로에는 없다.

결과: 실제 적용하면 소리가 달라지는데 A/B로는 변경을 판단할 수 없다. W3의 Insert 첨부 → 비교 → 채택 흐름을 막는다.

수정: 명시적으로 선택한 비교 구간을 우선 사용하고, 없다면 해당 Insert에 신호를 보내는 배치를 찾아 범위를 제안한다. 패널에 실제 비교 범위를 표시하고 조정 수단을 제공한다. 범위 내에 대상 신호가 없으면 그 사실을 안내한다.

회귀 조건: 도입부가 비고 뒤쪽에서만 소리가 나는 Insert의 효과 제안에서 해당 구간을 미리듣는다. 렌더 성공뿐 아니라 선택된 범위와 실제 오디오를 확인한다.
